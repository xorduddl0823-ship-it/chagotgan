보내는 곳: 홈페이지·앱 방
받는 곳:   서버 방 (넘김 코드를 받는 쪽 화면은 워시 방 · 체크 방 · 딜러 방에도 같이 알림 — 총괄 방이 나눠 줌)
제목:      메인 홈페이지 통합 로그인 — 휴대폰 인증 · 가게 목록 · 한 번짜리 넘김 코드 · 계정 없음 → 가입 이어 가기 · 사업자번호 겹침 → 승인 대기

1. 왜 필요한가요?
   대표님 결정(10/19 · 운영/04 «메인 홈페이지 = 통합 입구 A안»): 손님은 cgg.co.kr 홈페이지에서 한 번만 로그인하면
   자기 가게에 맞는 제품(워시 app.cgg.co.kr · 체크 check.cgg.co.kr · 딜러 dealer.cgg.co.kr)으로 다시 로그인 없이 들어가요.
   한 사람(같은 휴대폰)이 사업자가 다른 가게 여러 곳의 대표나 직원일 수 있어요 → 둘 이상이면 «가게 고르기».
   사업자번호 하나 = 업체 하나 규칙은 그대로예요. 지금 쓰는 app · check 로그인은 그대로 둬요.

2. 무엇을 해 주면 되나요? (cgg-api 에 창구 3개 + 받는 쪽 창구 1개 — 이름은 서버 방이 바꿔도 돼요, 바꾸면 알려 주세요)
   화면은 이미 만들었어요: 홈페이지/소개/로그인_v3.js (시안 0_차곳간_홈페이지_v3_시안.html · 주소 끝 #demo 로 예시 모드)
   부르는 모양은 지금 통합 입구와 같아요: POST cgg-api  body {shop:"", token, fn, args}

   ① homeOtp  args [휴대폰번호(숫자만)]
      → 인증번호 6자리를 알림톡(안 되면 문자)으로 보내요.  돌려줄 것 {ticket, to:"010-****-1234"}
      - 계정이 없는 번호여도 **같은 모양으로** 답해요(누가 가입했는지 알아내지 못하게). 그때는 보내지 않거나, 보내도 ③에서 가게 0곳.
      - 번호당 · 접속처당 보내기 횟수 제한(예: 10분 5번), 인증번호 유효 5분(화면에 «5분 안에 넣어 주세요»), 틀림 5번이면 그 ticket 끝.

   ② homeVerify  args [ticket, 인증번호]
      → 맞으면 {token, name, places:[{id, name, product, role}]}
        - token: 홈페이지 전용 짧은 표(예: 10분) — ③에만 쓰고 제품 로그인에는 못 써요.
        - places: 이 휴대폰이 대표 · 직원으로 들어 있는 **가게마다 한 줄**. product = "wash" | "check" | "dealer", role = "owner" | "staff" | "manager" | "dealer"
          id 는 겉으로 보여도 되는 값(가게 내부 번호를 그대로 드러내지 않아도 돼요).
        - 쓰지 못하게 막힌 계정(active=false)은 빼요.
      → 틀리면 __err 에 쉬운 우리말(예: «인증번호가 맞지 않아요. 다시 확인해 주세요.»)

   ③ homeGo  args [place id]   token = ②의 token
      → 그 가게 제품 주소 + 한 번짜리 넘김 코드: {url:"https://app.cgg.co.kr/#go=코드"} (체크는 check.cgg.co.kr, 딜러는 dealer.cgg.co.kr)
        - 코드: 맞히기 어려운 무작위 16자 이상(영문 · 숫자 · - _), **유효 60초 · 한 번만 · 그 가게 · 그 사람에만** 묶임.
        - 코드는 주소의 # 뒤에만 넣어요(서버 기록 · 다른 사이트로 새지 않게). 화면은 이 모양이 아니면 넘어가지 않아요.

   ④ (받는 쪽) 제품 화면이 주소의 #go=코드 를 읽어 서버에 «코드 바꾸기»를 부르면
      → 서버가 코드 확인(시간 · 한 번만 · 가게 · 사람) 뒤 그 제품의 지금 로그인과 같은 열쇠(워시 ccw_sid · 체크 cgg_key 등)를 줘요.
      → 화면은 바로 주소에서 #go=… 를 지워요(history.replaceState). 이 부분은 워시 · 체크 · 딜러 방이 화면을 고쳐야 해요.

   ⑤ (대표님 결정 10/19 추가) 계정 없음 → 회원가입으로 이어 가기
      → ② homeVerify 에서 가게가 0곳이면 places:[] 와 함께 joinToken 을 줘요(무작위 16자 이상 · 유효 10분 · 한 번만 · 그 휴대폰에 묶임).
        화면은 joinToken 을 같은 주소(cgg.co.kr) 안 sessionStorage 로만 회원가입 화면(join v7)에 건네고, 회원가입은 번호를 다시 묻지 않아요.
      → 회원가입 창구(지금 wash-api 의 agree · joinCheck · signup)가 휴대폰 번호 자리 대신 joinToken(vt)을 받으면 서버가 그 번호로 처리해 주세요.
        화면이 보내는 모양(시안 홈페이지/join_v7_시안.html):
          joinCheck [ "" , vt ]   → {why} (지금처럼 가입 코드 · 자유 가입 여부)
          agree   [ "" , {terms,privacy,refund}, 마케팅동의, 브라우저, vt ]
          signup  [ "" , 상호, 업종, 비밀번호, 대표자, 요금제, 사업자등록번호(숫자 10자리), vt ]
        (홈페이지를 거치지 않은 예전 가입은 지금처럼 phone 을 넣고 vt 는 빈칸)

   ⑥ (대표님 결정 10/19 추가) 사업자등록번호 겹침 → 승인 대기
      → signup 에 사업자등록번호가 새로 들어와요(사업자번호 하나 = 업체 하나 규칙 그대로).
        - 처음 등록되는 번호: 승인 없이 바로 가입 · 사용(지금 signup 답 {shop, payWait} 그대로).
        - 이미 등록된 번호와 겹침: 업체를 새로 만들지 말고 «가입 요청(승인 대기)»만 남기고 {pending:true} 로 답해요.
          화면은 «이미 등록된 사업자번호예요. 차곳간 확인 뒤 연결돼요» + «승인 대기» 화면을 보여 주고,
          «확인이 끝나면 이 번호로 알려 드려요»라고 안내해요 → 승인 · 거절을 알리는 길(관리 화면 · 알림)도 정해 주세요.
        - 겹쳤는지 여부를 가입 전에 따로 물어볼 수 있는 창구는 만들지 말아 주세요(남의 사업자번호 가입 여부를 알아내지 못하게).
      → 지금 회원가입은 워시 요금제만 고르는 화면이에요. 체크 · 딜러 가입 길은 이번 요청 밖이에요.

   ⑦ 보안 방 조건 12가지 (10/19 미리 검토 · 전문 보안/검사기록/2026-10-19_통합로그인_A안_시안.md — 꼭 같이 봐 주세요)
      1) homeOtp 는 없는 번호에도 실제로 보내니 번호 · 접속처 · 전체 하루 상한.
      2) ticket 은 한 번만, 틀린 횟수는 조건부로 먼저 올리기.
      3) token 32자 이상 · 10분 · 해시로 저장 · homeGo 에만.
      4) places id 는 가게 코드가 아니라 그 token 안에서만 뜻이 있는 값. 본사 · 막힌 계정 · 잠긴 업체는 빼기.
      5) homeGo 때 소속 다시 확인. 넘김 코드 24자 이상 · 60초 · 한 번만 · {제품 · 업체 · 번호 · 역할}에 묶어 해시로 저장.
      6) 코드 바꾸기는 POST 몸통으로만 · 조건부 지우기 한 번으로. 열쇠는 각 제품의 보통 로그인 규칙(잠금 · 기기 · 명단 · 동의)을 거쳐 주고, 본사 계정은 이 길로 열지 않기.
      7) 받는 쪽 화면은 #go 를 서버 부르기 전에 replaceState 로 지우기.
      8) vt 는 joinCheck · agree 에서 읽기만, signup 이 조건부로 써서 없애기. vt 가 있으면 화면이 보낸 phone 은 무시.
      9) 사업자번호는 서버가 10자리 · 끝자리 다시 검사. 겹치면 요청만 남기고 승인은 본사만. hq_audit 에 남기고 기존 대표에게도 알리기.
      10) pending 답으로 겹침 여부가 드러나는 건 남는 위험 — vt 가 있어야만 사업자번호를 받고, 하루 3번 제한, 기록 남기기.
      11) DB 에 10자리 유일 색인 · 가입 요청 표 따로 · 트랜잭션.
      12) 번호를 가린 기록 남기기.
      (위 «넘김 코드 16자 이상»은 24자 이상으로 — 화면 검사식도 맞춰 둘게요)

   ⑧ 챗지피티 1차 검수 Q3(운영/긴급/챗지피티_검수_중복사업자번호_1차결과.md)가 더 요구한 넘김 코드 조건 — 총괄 10/19 «요청서에 더하기»
      - 예측 불가 코드 · 서버엔 해시만 · 짧은 만료 · DB 에서 원자적 1회 소비(동시에 두 번 바꾸면 한 건만 성공).
      - 코드에 user · 업체(tenant) · 허용 역할 · 목적 제품 · 정확한 돌아올 주소 · 그 인증 시도를 묶기. 요청자가 보낸 아무 업체 id 로 다시 만들지 않기.
      - 교환할 때 목적 제품에서 지금 소속 · 활성 상태 · 제품 이용권 · 세션 철회를 다시 확인.
      - 로그인 시도와 state/nonce · PKCE S256 으로 묶기(코드 탈취 · 로그인 CSRF · 코드 끼워 넣기 막기). 다른 브라우저 · 제품 · 돌아올 주소에서 교환 거절.
        → 서버 방이 방식을 정하면 홈페이지 화면(로그인_v3.js)에 state · verifier 만들기를 붙일게요. 가능하면 검증된 OAuth/OIDC 방식으로.
      - HTTPS · 정확한 돌아올 주소 목록(app · check · dealer.cgg.co.kr 만) · 아무 주소로 보내기 금지. 코드 · 표를 로그 · 분석 · Referer 에 남기지 않기.
      - 받는 쪽 화면은 #go=코드 를 **받자마자** 주소에서 지우고(replaceState), 그 화면은 Cache-Control: no-store · Referrer-Policy: no-referrer.
      - 목적 서버가 새 세션을 만들어요. 오래가는 세션 열쇠를 주소로 건네지 않기. 본사 로그인 · 권한 올리기는 업체 코드로 대신 못 하게.
      - 로그아웃 · 퇴사 · 권한 바뀜 · 휴면 · 번호 재할당 때 남은 세션과 넘김 코드를 어떻게 끊는지 규칙 적기.

3. 끝났다고 보는 기준
   - 시험 주소(t.cgg.co.kr/home/)에서 TEST 번호로: 가게 1곳 → 바로 그 제품이 로그인된 채 열림 / 가게 2곳 이상 → «가게 고르기» → 고른 곳이 열림 / 가게 0곳 → «가게가 없어요».
   - 같은 넘김 코드를 두 번 쓰면 안 열림, 60초 지나면 안 열림, 다른 가게 id 로 바꿔 부르면 안 열림.
   - 지금 app.cgg.co.kr · check.cgg.co.kr 로그인은 그대로 됨.
   - 가입 안 된 번호로 인증 → 회원가입이 번호를 다시 묻지 않고 요금제부터 → 새 사업자번호면 바로 가입 / 겹치는 번호면 «승인 대기»와 요청 1건만 남음.
