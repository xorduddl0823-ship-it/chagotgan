[검수 요청] 성능점검 이중등록 프로그램 (carcheck-dual) — 현재 상태 요약
기준: 2026-10-18, 사용자 PC 폴더(C:\Users\admin\Documents\carcheck-dual) 실제 코드
(이 압축 파일에는 node_modules·dist(빌드 결과물)는 빠져 있습니다. 1_준비.bat 로 다시 받을 수 있습니다.)

■ 1. 무엇을 하는 프로그램인가
- 중고차 성능점검 결과를 두 기관 사이트에 손으로 두 번 입력하던 일을, 한 번 입력으로 두 곳에 자동으로 채워 주는 윈도우 PC 프로그램.
  · 경기조합 성능점검관리시스템: ck.carmodoo.com (JSP/Spring, jQuery 1.9, 등록 화면은 팝업 + iframe)
  · 카인포 성능점검 관리시스템: ai.carinfo.co.kr (Vue + jQuery + Bootstrap5, DataTables)
- 두 사이트 모두 공개 API 없음 → 로그인된 사이트 화면을 프로그램이 대신 조작하는 방식.

■ 2. 작동 방식 (구조)
- Electron 앱 (electron ^32, electron-builder ^25). Playwright 안 씀.
- 창 3개: ① 통합 입력 화면 ② 경기조합 창 ③ 카인포 창.
  사이트 창은 세션 파티션(persist:carmodoo / persist:carinfo)이라 로그인이 앱에 유지됨.
- 값 넣기: 메인 프로세스가 webContents.executeJavaScript 로 사이트 페이지에 스크립트를 주입해
  칸 채우기·라디오/체크 선택·버튼 클릭을 함. iframe 안까지 훑음(runInFrames).
- 사진: Chrome DevTools Protocol(webContents.debugger) 의 Page.setInterceptFileChooserDialog 로
  파일 선택창을 막고 DOM.setFileInputFiles 로 경로를 직접 꽂음.
- 엔터 키가 필요한 곳은 sendInputEvent(진짜 키) → 사이트 함수 직접 호출 → 가짜 키 이벤트 순으로 시도.
- 화면 이동·대기는 메인 프로세스가 하고, 주입 스크립트는 "지금 상태"만 짧게 확인함
  (페이지가 새로 그려지면 주입 스크립트가 죽기 때문).
- 모든 대기에 시간 제한 있음 (로딩 15초, 상태확인 5초, 신규등록 전체 2분 등).

■ 3. 파일 구성 (약 9,000줄)
- main.js (2,035줄): 창 관리, IPC 25개, 화면 준비, 사진 업로드 조종, 딜러 선택, 자동 로그인
- preload.js: 화면 ↔ 메인 통신
- src/schema.js: ★ 통합 항목 121개 + 두 사이트 매핑(선택자·코드값 변환). 단일 기준 파일
- src/filler.js (1,223줄): 앱 → 사이트 값 넣기 (절개도 부위 표시 포함)
- src/scraper.js: 사이트 → 앱 되읽기 (카인포 원부 정보 가져오기)
- src/carinfo-prepare.js: 카인포 신규등록 자동 진행
- src/carinfo-dealer.js / carmodoo-dealer.js: 딜러 검색·선택 (두 사이트)
- src/carmodoo-lookup.js: 경기조합 차량번호 조회 → 차대번호 전체 가져오기
- src/photo-upload.js: 사진 8칸 업로드 (두 사이트 공용)
- src/accident-probe.js, carinfo-learn.js: 사고 부위(절개도) 구조 조사·학습용
- src/credentials.js, auto-login.js: 로그인 정보 암호화 보관 + 자동 로그인
- renderer/: 입력 화면 (app.js, parts-diagram.js 절개도 그림, photos.js 사진칸)
- tools/: 절개도 부위 위치 맞추는 보조 도구 (브라우저용)

■ 4. 사용 순서 (현재 구현)
① 설정에서 두 사이트 아이디·비밀번호 저장(선택) → 자동 로그인. 또는 각 창에서 직접 로그인.
② 차량번호 + 딜러명만 입력.
③ [신규등록 + 차량정보·차대번호 가져오기]
   카인포: 성능점검 화면 이동 → 공지팝업 닫기 → 목록 DataTable 준비 대기 → [신규등록] →
   차량번호 → 딜러 검색 → [선택] 실제 클릭 → [확인] → 원부 조회 → 등록 화면 진입 →
   원부 값(차명·연식·최초등록일 등)을 앱으로 되읽어 채움.
   경기조합: 차량번호 조회로 차대번호 전체를 받아 카인포 뒷 6자리를 채움(vin:sync).
④ 점검 항목·사고 부위(절개도)·사진 8칸 입력 → [두 곳 동시 전송]
   경기조합은 딜러·상사 선택을 먼저 하고(안 하면 "상사가 선택되지 않았습니다"), 나머지 값 → 사진 순.
⑤ 각 사이트 창에서 사람이 확인 후 직접 [저장]. (최종 등록 저장은 자동으로 누르지 않음, autoSubmit=false)
   단, 절개도 부위 팝업 안의 [저장](팝업 닫기용)은 프로그램이 누름.

  diagram.json, pillar.json, carinfo-parts.json, photo-probe.json)

■ 6. 확정된 설계 원칙
- 최종 저장은 사람이 누른다 (잘못된 성능기록부 등록 방지).
- 동명이인 딜러는 자동으로 고르지 않고 목록을 띄워 사람이 고른다
  (실제 사례: "신동민" → 판다카/솔카 2명). 경기조합은 이름·상사·연락처가 모두 맞을 때만 자동 선택.
- 원부 값과 입력값이 다르면 입력값 유지 + 차이 알림.
- 리콜 대상/이행 코드값이 두 사이트에서 정반대 → schema.js 에서 뒤집어 보냄.
- 로그인 정보: 원래 "저장 안 함"이었으나 자동 로그인 도입하며 변경.
  Electron safeStorage(윈도우 DPAPI)로 암호화 저장, 암호화 불가 환경이면 저장 거부, 화면·로그에 비밀번호 안 남김.

■ 7. 개발 중 실제로 겪고 고친 문제
- 딜러 값만 넣으면 카인포 [확인]이 안 됨 → [선택] 버튼을 실제 클릭해야 함.
- 메뉴 클릭/화면 새로고침 시 주입 스크립트가 죽음 → 이동·대기는 메인 프로세스가 담당.
- [신규등록]은 눌리는데 팝업이 안 뜸 → 핸들러가 목록 DataTable을 먼저 건드림 → DataTable 초기화까지 대기.
- 스피너 무한 대기 → did-finish-load 만 기다린 탓 → 전 구간 시간 제한.
- 경기조합 등록 화면을 주소로 바로 열면 부모 창이 없어 딜러 선택값이 안 들어감 → 목록에서 [접수등록]으로 여는 방식으로 변경.
- 경기조합 사원선택 창이 window.opener 로 값을 못 돌려줌 → 표의 값을 앱이 직접 넣음.
- 팝업을 GET으로 열어 카인포 사진등록이 405 → 팝업을 진짜 창으로 열도록 변경.
- 카인포 사진 칸 위치를 잘못 잡아 앞·뒷면이 한 칸에 들어감 → 좌표로 이름표-상자 짝짓기, 올린 뒤 바뀐 칸 확인.
- 사진 8장 7.3초 → 1.5초로 단축.

■ 8. 아직 확인 안 됐거나 남은 것
- 실제 차량 1건을 두 사이트 모두 끝까지 저장까지 완주했는지 기록으로 확인되지 않음 (최우선 확인 필요).
- 카인포 절개도: 필러 A·B·C 부호 정보 비어 있음(학습 재실행 필요), 외판 일부의 수리 부호(부식·흠집·요철·손상)는 자리 확인 방법이 없어 비워 둠.
- 튜닝 구분: 카인포는 구조·장치 동시 선택 가능, 경기조합은 하나만 → 하나만 보냄.
- 두 사이트 성능번호 체계가 달라 하나로 못 합침.
- 보험료 자동산출(카인포), 조합 정산 항목은 미구현.
- 두 기관 이용약관상 자동화 허용 여부 미확인.
- 자동 테스트 코드 없음 (화면 직접 실행으로만 확인해 옴).

■ 9. 검수 때 특히 봐 줬으면 하는 점
1) 비밀번호 암호화 보관·자동 로그인 방식이 안전한지 (safeStorage/DPAPI, 주입 스크립트에 비밀번호를 JSON 문자열로 넣는 방식).
2) README.md 내용이 코드와 어긋남: 맨 아래 "비밀번호를 저장하지 않는다", "사진 업로드 미구현",
   "경기조합 차량번호 조회 미연동"이라고 남아 있으나 실제로는 셋 다 구현됨 → 문서 정리 필요.
3) 진단·학습용 버튼(사고체크 구조 조사, 카인포 절개도 학습, 팝업 진단, 사진 화면 조사)이 일반 입력 화면에 그대로 노출됨 → 직원용에서는 숨길지.
4) main.js 2,000줄·filler.js 1,200줄로 커짐 → 나눌 필요가 있는지.
5) DevTools Protocol(debugger.attach) 사용, 업로드 중 alert 막기 등 사이트를 강하게 조작하는 부분의 위험.
6) 사이트 개편 시 깨지는 지점이 schema.js 한 곳으로 모여 있는지, 아니면 여러 파일에 흩어졌는지.
