# 12차 보완 — 관찰 결과로 채울 설정 대응표 · 실제 자동등록 합격 기준 (2026-10-19)

> 관찰 기록 파일을 받으면 `node tools/observe-map.js <파일>` 로 쓰기 요청을 «8초 안에 바로 앞에 누른 단추»와 짝지어 정리한다.
> **이 짝짓기는 추정이다** — 도구의 모든 후보는 `confirmed:false`, 도구는 설정 파일을 고치지 않는다. 사람이 화면 기록·시간 순서와 함께 하나씩 확인한 항목만 `src/sites/site-config.js` REAL 에 넣고, `tools/config-check.js` CONFIRMED 에 근거(파일 이름·확인한 것)를 적는다.
> 응답 번호(200 등)만으로 등록 성공을 정하지 않는다 — 성공은 언제나 저장 뒤 목록·상세를 다시 읽어 확인한다(기존 register-flow 그대로).

## 1. 관찰 결과 → 설정 항목 대응표
| 전산 | 설정 | 관찰 기록에서 찾는 것 | 구분 기준 |
|---|---|---|---|
| 공통 | `savePatterns` | [저장] 단추 바로 뒤 쓰기 요청 주소 | 정확히 «저장» 글자 단추 뒤 · 하나여야 함(여러 개면 화면 기록으로 확인) |
| 공통 | `readAllow` | 저장 전·후 조회 요청(GET·xhr) 중 저장 중에도 나가야 하는 것 | 주소에 저장 같은 말이 없고 GET |
| 공통 | `fillAllow` | 값 넣기 중 나가는 쓰기 요청(딜러 조회 등) | [저장] 앞 · 단추 없이 나간 쓰기 → **사람이 하나씩 확인 뒤에만** |
| 공통 | `list.rows/cols` | 목록 화면 칸 기록(표 머리글·줄 수) | 화면 칸 기록 |
| 카인포 | `phaseAllow.prepare` | [신규등록] · [확인] 뒤 쓰기 요청 | 신규등록이 값 넣기·[저장]보다 먼저인지 시간 순서로 확인 |
| 카인포 | `phaseAllow.photo` | [사진만 전송 (카인포)] 뒤 쓰기 요청(파일 올리기 모양) | 짝지은 단추가 맞는지 사람 확인 |
| 카인포 | `photoPhase` | 사진 요청과 [저장] 요청 중 어느 것이 먼저인가 | **확인 전 — 지금 설정은 비어 있음(null)**. 사진이 있는 차는 저장 단계로 가지 않고 멈춤. 관찰된 순서(도구의 «사진·저장 순서»)를 사람이 확인한 뒤에만 `beforeSave`/`afterSave` 로 정함 |
| 카인포 | `list.savedStatus` · `vinFromForm` | 저장 뒤 목록 «점검완료» · 줄을 눌렀을 때 차대번호 칸 | 화면 칸 기록 |
| 경기조합 | `manualInput` · `numberField` | «수동입력» 체크 칸 · 점검번호 칸 이름 | 수동입력 클릭이 서버 요청을 보내는지 따로 표시(저장과 구분) |
| 경기조합 | `phaseAllow.photo` · `photoPhase` | [사진만 전송 (조합)] 뒤 쓰기 요청 · [저장]과의 순서 | 시간 순서 |
| 엔트리 | `loggedIn` · `quick.numberInput` | 로그인 표시 칸 · [간편 접수] 창 번호 칸(**읽기만**) | 화면 칸 기록 |
| 엔트리 | `loadRetry.pureRead` | [불러오기] 뒤 쓰기 요청이 있는지 | 쓰기 요청이 있으면 다시 하기 금지 유지 |
| 엔트리 | `loaded.*` · `detail.*` | 불러온 화면·상세 화면의 성능번호·차량번호·차대번호 칸 | 화면 칸 기록 |
| 엔트리 | `savePatterns` | [저장] 뒤 쓰기 요청 | [불러오기] 요청과 다른 주소인지 확인 |

## 2. 실제 자동등록 운영 전환 합격 기준 (10/26 은 목표일 — 기준을 다 넘어야만 켬)
| # | 기준 | 확인 방법 | 합격 |
|---|---|---|---|
| 1 | 세 전산 화면 설정 확정 | 관찰 기록 근거로 `tools/config-check.js` 미확정 0(필수 항목) | 근거 칸이 모두 «관찰/진단: 내부 이름 확인» |
| 2 | 저장 요청 통제 | 시험판에서 «저장 직전까지» 실행 — [저장] 전 쓰기 요청이 통제기에 막히는지, 값 넣기 요청은 나가는지 | 세 전산 모두 저장 전 쓰기 0건(허용한 것 제외) |
| 3 | 실제 저장 1대 | 대표님 입회 · 정상 업무 차 1대 · 자동 [저장] | 세 전산 번호 같음 · 목록·상세로 차량번호·차대번호 17자리 확인 |
| 4 | 중복 방지 | 같은 차 다시 실행 · 저장 결과 불확실(창 닫힘 등) 흉내 | 다시 저장 0건 · 목록 확인으로만 진행 |
| 5 | 번호 규칙 | 엔트리 번호 칸 손대지 않음 · 번호 다르면 멈춤 | 실제 1대에서 확인 |
| 6 | 엔트리 재인증 | 엔트리 로그아웃 상태에서 시작/도중 | 멈춤 → 재인증 → 남은 단계부터, 카인포·카모두 다시 등록 0건 |
| 7 | 오류 복구 | 프로그램 종료 후 다시 켜기 · 이어 하기 | 작업 기록으로 이어 감 · 끝난 전산 다시 저장 0건 |
| 8 | 데이터 분리 | 시험판 묶음 검사(`tools/verify-test-bundle.js`) | 업무용 기록 폴더 변화 0 |
| 9 | 현장 시험 | 실제 업무 차 여러 대(대표님 입회) | 중대한 오류 0건(잘못된 차·번호 불일치·중복 저장·데이터 손실) |

기준을 못 넘은 전산은 자동 저장을 켜지 않고(`confirmed:false`) 기존 업무 방식(값 자동 입력 + 직원 [저장])을 유지한다.
