# 15차 — 웹 단일 화면 전환: 기술 가능성 · 재사용 범위 · 가장 빠른 구현안 (2026-10-19)

> 이번 차수는 **검토 보고**입니다. 새 프로그램은 만들지 않았습니다.
> 근거: 저장소의 차곳간 CHECK 웹 소스(`체크/`), 체크 서버(`서버/2_차곳간체크_서버_check-api_v52.ts`), 13·14차 Windows 소스(`통합등록/carcheck-dual`).
> 실제 세 전산(카인포·카모두·엔트리)에는 지금까지 한 번도 접속하지 않았습니다. 실제 사이트 동작은 대표님 화면 사진과 12차 사고 결과로만 압니다.

## 1. 결론
- **가능합니다. 다만 조건이 하나 있습니다.** 직원 화면은 차곳간 CHECK 웹 하나로 만들 수 있습니다.
- **조건:** 세 전산을 조작하는 일은 웹페이지 안에서 직접 할 수 없습니다. 브라우저 보안 규칙 때문에, 한 사이트의 웹페이지는 다른 사이트(카인포·카모두·엔트리)의 로그인 상태와 화면을 읽거나 누를 수 없습니다.
- **해결:** 가온검사소 PC 한 대에 **뒤에서 도는 실행기**를 두고, 웹이 그 실행기에 일을 맡깁니다.
  - 실행기는 13차 엔진을 그대로 재사용하고, 직원이 볼 화면은 없습니다.
  - 직원은 웹만 봅니다. 실행기 PC는 켜 두기만 합니다.
- **최대 걸림돌은 구조가 아니라 실제 사이트 정보입니다.** 실제 사이트 설정 47개 중 44개가 미확정입니다. 저장 요청 주소, 목록 칸, 엔트리 칸, 사진 순서가 여기에 들어갑니다.
  - 그래서 어떤 구조를 고르든 **완전 자동 등록은 실제 등록 관찰 기록을 받은 뒤에야** 켤 수 있습니다.
  - 이 사실은 웹 전환으로 바뀌지 않습니다.

## 4. 직원 단일 웹 화면 흐름(제안)
1. **입력** — 차량번호·딜러 → [차량정보 가져오기](실행기가 카모두에서 조회해 웹 칸을 채움) → 점검 항목·절개도 → 사진 8장.
2. **등록 요청** — [세 전산 등록] 한 번. 같은 차가 진행 중이거나 오늘 이미 등록돼 있으면 서버·실행기가 막고 이유를 표시합니다.
3. **상태판** — 카인포 / 카모두 / 엔트리 줄마다 «대기 → 입력 중 → 저장 확인 중 → 완료(번호)» 또는 «멈춤(원인 · 지금 저장 상태 · 할 일)»을 보여 줍니다.
4. **멈춤 처리(웹에서)**
   - 칸 고치기 → [다시 검증]
   - 딜러 고르기
   - 엔트리 인증 글자·번호 입력
   - [목록 다시 확인]
   - 웹에서 못 하는 일(저장 뒤 정정 등)은 «원본에서 할 일»로 따로 표시
5. **완료** — 세 전산 모두 «저장 확인 + 번호·차량번호·차대번호 일치»일 때만 **완료**로 표시합니다. 하나라도 확인 전이면 완료라고 쓰지 않습니다.

## 5. 웹 안에서 해결 가능한 오류 범위
- **웹에서 끝남:** 저장 전 오류(값·필수 칸) · 딜러 동명이인 · 엔트리 인증(△ 허락 시) · 불확실 → 목록 재확인 · 사진 다시 고르기(저장 전 단계일 때) · 실행기 꺼짐/로그인 만료 안내
- **원본 사이트가 필요함(웹에는 안내만):** 이미 저장된 기록의 수정·삭제·중복 정리 · 사이트 관리자 정정 · 예상 밖 화면(팝업·공지)에서 사람이 판단할 때 · 계정 비밀번호 변경

## 6. 가장 빠른 최소 구현안(가온 단독)
| 단계 | 내용 | 담당 방 | 재사용 | 실제 사이트 필요 |
|---|---|---|---|---|
| A | **실행기**: 13차 프로그램을 «화면 없는 뒤 실행 모드」로 — 서버에서 작업을 가져와 기존 엔진(runAll·값 넣기·신규등록·딜러·사진·검증)으로 처리하고 상태를 올림. 실제 설정 미확정이면 저장 직전에 멈춤(지금과 같음) | 통합등록(이 방) | 엔진·사이트 조작·안전장치 전부 | 아니오(흉내 사이트로 완성) |
| B | **서버**: «등록 작업» 표(차량 자료·사진 위치·전산별 상태·번호·멈춤 이유) · 함수(작업 만들기·가져가기·상태 올리기·딜러 고르기·인증 글자 전달) · 실행기 기기 토큰 | 서버 방 | check-api 구조·Storage | 아니오 |
| C | **웹 화면**: 입력(13차 화면 옮김) · 사진 올리기 · [세 전산 등록] · 상태판 · 멈춤 처리 | 체크 방(+ 디자인 기준틀) | `schema.js`·`renderer` 화면 코드 | 아니오 |
| D | **실제 등록 관찰** 기록 → 세 전산 설정 확정(저장 주소·목록·엔트리 칸·사진 순서) | 통합등록 + 대표님 | 관찰 기록 도구(12차) | **예** |
| E | 실제 «저장 직전까지» → 대표님 입회 실제 저장 1대 → 현장 | 통합등록 + 대표님 | — | **예** |

- **A·B·C는 실제 사이트 없이 동시에 만들 수 있습니다.** 흉내 사이트로 웹 → 서버 → 실행기 → 상태판까지 «한 번 입력 → 결과 확인»을 끝까지 보여 줄 수 있습니다.
- **D가 늦어지면 완전 자동도 늦어집니다.** 그 사이에도 «웹 입력 → 실행기가 값만 넣고 저장 직전 멈춤 → 직원이 실행기 PC 에서 [저장]» 단계로 쓸 수는 있지만, 최종 목표(웹 하나)는 D 이후입니다.

## 7. 13차 문제를 새 구조로 옮기지 않는 장치
| 13차 문제 | 새 구조에서 |
|---|---|
| 카모두 사진 자리 = 접수 등록 → 중복 | 사진 자동 올리기 꺼짐 유지. 순서는 실제 관찰로 확인한 뒤에만 켬. 새 접수 전 리스트 전체 확인(여러 쪽·Total) — 14차 그대로 |
| 같은 차 중복 등록 | 서버가 같은 차 «진행 중 작업»을 하나만 허용 + 실행기가 각 전산 목록 확인 — 이중으로 막음 |
| 사진 업로드 실패 | 전산별 «사진 단계»로 따로 표시 · 실패해도 접수를 다시 만들지 않음 |
| 팝업·대기에서 멈춤 | 알림창 감시(즉시 멈춤) · 모든 단계 시간 제한 · 실행기가 멈추면 웹에 «실행기 응답 없음» |
| 저장 검증 부족 | 완료 = 목록·상세 재조회로 번호·차량번호·차대번호 확인된 경우만 |
| 테스트와 실제의 차이 | 보고서마다 «단위 / 모의 사이트 / 실제 웹 시스템 연동 / 실제 Windows» 네 칸으로 나눠 적고, 모의 성공을 운영 성공이라 쓰지 않음 |

## 8. 위험 · 제약
1. **엔트리 보안문자·문자 인증:** 웹에서 직원이 입력하고 실행기가 그대로 넣는 방식은 우회가 아니라 «사람이 하는 입력을 전달»하는 것입니다. 하지만 인증 정보가 서버를 지나가므로 **보안 방 검토와 대표님 허락**이 필요합니다. 허락하지 않으면 엔트리 로그인만 실행기 PC 에서 직원이 직접 합니다(약 30분마다).
2. **실행기 PC:** 가온 PC 한 대가 켜져 있어야 합니다. 꺼지면 웹에 «실행기 꺼짐»이 보이고 등록은 대기합니다. 계정 정보는 그 PC 에만 암호화해 둡니다(13차 방식).
3. **사이트 이용 조건:** 공식 API 가 없어서, 가온 계정으로 정상 화면을 조작하는 방식입니다. 각 전산 이용 조건상 자동 조작이 허용되는지는 대표님 판단 사항입니다.
4. **실제 사이트 미확정 44개:** D 단계 전에는 실제 자동 저장을 켜지 않습니다.

## 9. 대표님이 정할 것(3가지)
1. **구조 승인** — 직원 화면은 체크 웹, 가온 PC 한 대에 뒤 실행기. **추천.**
2. **엔트리 인증을 웹에서 입력 → 실행기 전달** 방식 검토 진행(보안 방) — 허락 전까지는 실행기 PC 에서 직접 로그인.
3. **실제 등록 관찰 날짜** — 이것이 완전 자동의 출발점입니다.
