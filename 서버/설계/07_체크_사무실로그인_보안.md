# 체크 사무실 로그인 보안 (check-api v26 → **v28** · 2026-10-15 · 배포 전)

> **v28 갱신 (보안 방 재검사 권고)**: `login` 이 확인 번호를 보낼 때 무작위 **tick** 을 함께 돌려줘요(`{__err, __need: "code", __tick}`).
> `loginCode(휴대폰, 확인번호, tick, (검사소코드), UA)` 는 그 tick 과 짝이 맞을 때만 받아요. 다른 사람이 중간에 login 을 다시 해서 비밀번호를 바꿔치기하는 길이 막혀요.
> 문자에는 「본인이 로그인한 게 아니면 넣지 마세요」가 붙어요. `sql/04` 를 다시 Run(tick 칸 추가, 여러 번 실행 안전). v27(자기 비밀번호 초기화 막기)도 포함.
> 시험 `서버/시험/체크v28_로그인_시험.ts` 22개 통과 (v27 로 돌리면 4개 실패).

> 보안 방 요청(2026-10-15, `보안/검사기록/2026-10-15_체크묶음_서버v25_기사화면v24.md`)에 대한 답이에요.
> v26 = v25(직원 권한 창구) + 아래 두 가지. **먼저 `sql/02`(이미 있음)와 `sql/04_체크_첫비밀번호_문자확인.sql` 을 실행**해요.

## 바뀌는 것
1. **사무실 로그인 잠금** — 같은 번호로 비밀번호를 5번 틀리면 10분 잠겨요(한꺼번에 보내도 똑같이). 기사 로그인과 같은 횟수 장치(`check_deliv_attempt`, 열쇠 `office:번호`)를 써서 새 함수는 없어요.
   - 이미 정한 4~5자 비밀번호는 그대로 로그인돼요.
2. **처음 비밀번호는 문자 확인 뒤에** — 비밀번호가 빈 계정(대표가 새로 넣은 직원 · 비밀번호 초기화한 직원)은:
   1. `login(휴대폰, 새 비밀번호 6자 이상)` → 바로 들어가지 않고, 그 휴대폰으로 확인 번호 6자리 문자가 나가요. 응답은 `{__err: "처음 쓰는 비밀번호예요. … 확인 번호 6자리를 넣어 주세요.", __need: "code"}`.
   2. `loginCode(휴대폰, 확인번호, (검사소코드))` → 맞으면 1번에서 적은 비밀번호가 정해지고 바로 들어가요(`first: true`).
   - 확인 번호는 5분 동안만, 5번 틀리면 10분 잠금, 다시 로그인하면 새 번호가 나가고 예전 번호는 못 써요. 확인 번호는 표에 그대로 저장하지 않아요.
   - 문자 보내는 번호: 비밀값 `SMS_FROM`(워시와 같은 이름, 프로젝트 공용) → 없으면 그 검사소의 보내는 번호.
   - 그래서 「번호를 아는 다른 사람이 먼저 로그인해서 비밀번호를 정하는」 빈틈이 막혀요.

## 체크 방이 사무실 화면에 붙일 것
- 로그인 응답에 `__need: "code"` 가 오면 「확인 번호 6자리」 칸을 열고, 함께 온 `__tick` 을 기억했다가 `loginCode(휴대폰, 번호, __tick, 검사소코드, navigator.userAgent)` 를 불러요 (v28). 성공하면 보통 로그인과 같은 모양(`key` 등)이 와요.
- 처음 비밀번호 안내를 「6자 이상」으로.
- 직원 권한 카드 안내: 「새 직원은 처음 로그인할 때 휴대폰 문자로 확인해요」.
- ⚠ 이 칸이 없는 화면(v25)과 v26 서버를 같이 올리면, 새 직원·초기화한 직원은 확인 번호를 넣을 곳이 없어 못 들어와요(기존 직원은 상관없음). **v26 은 확인 번호 칸이 있는 사무실 화면과 함께** 올려요.

## 통합 입구(경비실)와의 관계
- 경비실은 이미 정해진 체크 비밀번호로만 확인해요. 그래서 처음 비밀번호는 위 문자 확인을 거쳐 체크 화면에서 먼저 정해야 통합 입구에서도 들어가져요(지금과 같음).
