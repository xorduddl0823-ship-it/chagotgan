# 설계 22 — 체크 차량 도착 알림을 «차곳간_출고안내» 알림톡으로 (운영/06 M ④ · 대표님 결정 10/17 밤 · check-api v34)

## 무엇을 바꿨나
- 차량 도착 알림(`notifyOne`)이 템플릿을 고르는 순서를 바꿨어요.
  - `tpl.check_arrive`가 있으면 그것을 먼저 써요. 아직 등록하지 않았어요.
  - 없으면 이미 승인된 **`tpl.release`(차곳간_출고안내)**를 써요.
  - 그다음은 검사소 `ata_tpl`(본사 목록 안의 것만)이고, 그것도 없으면 문자예요.
- 출고안내 템플릿을 쓸 때는 본문을 건드리지 않고 **변수만 채워요**. 원문은 알림톡/00_확정본_13개_원문.md 2번이에요.

| 변수 | 값 |
|---|---|
| 딜러명 | 배달 줄 dealer_name, 없으면 «-» |
| 상사명 | company_name, 없으면 «-» |
| 차량번호 | plate |
| 작업내용 | «성능점검 · 배달» (고정) |
| 목적지 | dest_name |
| 출고일시 | 도착 시각 (MM-DD HH:MM, 한국 시간) |
| 업체전화 · 업체명 | 검사소 tel · name |
| 보기코드 | **«d» + 배달 열쇠글(view_key 18자)** |

- 알림톡이 안 되면 대체 문자로 보내요. 글은 지금 검사소 도착 문자 그대로예요.
  - 다만 `[사진 주소]`는 **https://app.cgg.co.kr/v.html?c=d열쇠**로 바꿨어요. 10/17 시험에서 운영 체크 사이트 /d/ 화면이 열쇠를 못 읽었기 때문이에요.
- 이미 보낸 옛 /d/ 주소(추천): 운영 체크 사이트(check.cgg.co.kr, 체크 방 몫)가 `/d/열쇠`를 `https://app.cgg.co.kr/v.html?c=d열쇠`로 넘기게 해요.
  - Cloudflare Pages라면 `_redirects`에 `/d/:key https://app.cgg.co.kr/v.html?c=d:key 302` 한 줄을 넣으면 돼요. 올린 뒤 한 번 눌러 확인해요.
  - 서버는 «d» 없는 18자 열쇠도 그대로 받아요.
- 발송 기록 tpl 이름은 `check_arrive_release`예요.

## 버튼 주소와 v.html (워시 방 몫)
- 버튼은 `https://app.cgg.co.kr/v.html?c=#{보기코드}`로 고정이에요. 그래서 v.html은 `c`가 **소문자 d로 시작하면** 체크 서버를 불러요.
  - 워시 보기코드는 대문자 A–F와 0–9 24자예요. 체크 청구서는 «k»로 시작해요. 그래서 서로 겹치지 않아요.
  - 부르는 곳: check-api `{ fn: "deliv_view", args: [c 그대로] }`
  - 서버가 앞의 d를 떼요.
- 답은 `{ result: { office:{name, tel}, photos:[서명 주소 1시간], deliv:{plate, car, dest, driver, dealer, at} } }`예요. 잘못된 주소면 `{ __err }`예요.
  - 받는 번호는 답에 넣지 않아요.

## 보안
- `deliv_view`에 한 아이피당 하루 상한을 붙였어요. `CHECK_VIEW_IP_MAX`(기본 300)로 청구서 보기와 같아요.
- 열쇠글은 무작위 18자라서 찍어서 맞힐 수 없어요.
- 받는 번호 제한(등록된 딜러만), 하루 상한, 보내는 번호 규칙(v32 M2)은 그대로예요.
- SQL은 필요 없어요.

## 같은 판에 더한 것 — 딜러 등록 대기 (체크/기획/2026-10-17_딜러등록대기_설계.md · 보안 의견 ①~⑨)
- 기사가 처음 적은 번호로는 지금처럼 **보내지 않아요**(M2 그대로). 사무실이 승인해야만 보내요.
- 체크에는 매니저 역할이 없어서, 세 창구 모두 **대표만** 써요.

| 창구 | 하는 일 |
|---|---|
| `delivPendingDealers()` | 최근 14일 «등록된 딜러 번호가 아님»으로 못 간 기록을 번호로 묶어 줘요. 지금 등록된 번호, 보낸 건, 취소된 건, 휴지통 건은 빼요. |
| `delivApproveDealer({name, tel, dealerId?, companyId?, resend})` 또는 그 배열(20줄까지) | 아래 «승인할 때»를 보세요. |
| `delivRejectDealer({name, tel})` 또는 그 배열 | 그 기록의 err를 «딜러 등록 안 함(사무실)»으로 바꿔 대기에서 빼요. 기록은 남고, 알림은 안 가요. |

- `delivPendingDealers` 답의 줄마다 `{tel, names[], companies[], drivers[], n, first, last, match:[{id, name}]}`가 들어 있어요.
  - `match`에는 같은 이름의 기존 딜러가 들어 있어요. 화면이 «기존 딜러에 번호 더하기»를 먼저 보여 줄 때 써요.

**승인할 때 (`delivApproveDealer`)**
- 받은 이름과 번호가 대기 기록에 **실제로 있어야** 해요(⑥).
- 딜러를 넣어요.
  - `dealerId`가 있으면 이 검사소의 기존 딜러에 번호를 더해요(tels).
  - 없으면 새 딜러를 만들어요. `companyId`는 이 검사소 상사일 때만 붙여요.
- 그 번호로 못 간 기록 가운데 **24시간 안**, 아직 «보냄»이 아닌 것만 다시 보내요.
  - 글은 서버가 저장된 기록으로 다시 만들어요(notifyOne, cleanVars)(⑦).
  - 하루 상한을 지켜요.
- `check_log`에 «딜러 등록 승인» 기록을 남겨요. 번호는 가려요.
