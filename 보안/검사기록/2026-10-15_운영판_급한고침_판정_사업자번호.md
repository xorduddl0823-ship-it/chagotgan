# 운영 중인 판에도 있는지 — 사업자번호·알림톡 채널·캐시 (2026-10-15 · 보안 방)

> 총괄 질문: 바탕 검사 높음이 **지금 운영 중인** 체크 v21.2 · 워시 sb1 에도 있나? 운영 급한 고침 대상인가?
> 운영 판: 체크 `check-api v21.2`(오늘 아침 올림) · 워시 `wash-api sb1`(2026-10-14 배포본 원본과 지문 일치)

## 결론 (먼저)
- **있어요.** 사업자번호 바꾸기(체크 H1 · 워시 W-H1)는 두 운영 판 모두에 **같은 코드**로 있어요. 워시 알림톡 채널(W-H2)도 sb1 에 있고, sb1 은 화면이 보낸 템플릿·변수를 **그대로** 보내서 더 넓어요.
- **판정: 운영 급한 고침 대상 — 단, 코드 배포 없이 SQL 한 번으로 먼저 막는 것을 추천.** 세금계산서는 실제 발행·취소 불가라 한 번이면 되돌릴 수 없어요. 지금 쓰는 업체가 적어도(믿을 만한 손님뿐이어도) 막는 비용이 아주 작아요.
- 순서: ① 아래 **확인 SQL(읽기만)** 로 흔적 보기 → ② 흔적 없으면 **막는 SQL**(사업자번호·팝빌 칸을 처음 정한 뒤 못 바꾸게 + 같은 번호 두 곳 금지) → ③ 서버 고침은 sb14 · 체크 v31 로(시험 뒤 운영).

## ① 확인 SQL — 읽기만 (Supabase SQL Editor 에 붙여 넣고 Run)
```sql
-- 1) 체크: 같은 사업자번호·팝빌 번호를 둘 이상의 검사소가 쓰는지
select coalesce(nullif(regexp_replace(coalesce(popbill_corp,''),'[^0-9]','','g'),''), regexp_replace(coalesce(biz_no,''),'[^0-9]','','g')) as corp,
       count(*) as n, string_agg(code||'('||name||')', ', ') as offices
from check_office group by 1 having count(*) > 1;

-- 2) 체크: 검사소 설정을 고친 기록 중 사업자번호·팝빌 칸이 들어간 것 (최근 것부터)
select * from check_log
where what = '검사소 설정 고침'
  and (detail::text ilike '%biz_no%' or detail::text ilike '%popbill_corp%' or detail::text ilike '%popbill_userid%')
order by 1 desc limit 100;

-- 3) 워시: 같은 사업자번호를 둘 이상의 업체가 쓰거나, 차곳간 본사 번호를 쓰는 업체
select regexp_replace(coalesce(s.biz_no,''),'[^0-9]','','g') as biz, count(*) as n, string_agg(s.shop||'('||s.name||')', ', ') as shops
from wash_shops s where coalesce(s.biz_no,'') <> '' group by 1 having count(*) > 1;
select s.shop, s.name, s.biz_no from wash_shops s, wash_hq h
where h.id = 1 and regexp_replace(coalesce(s.biz_no,''),'[^0-9]','','g') = regexp_replace(coalesce(h.biz_no,''),'[^0-9]','','g') and coalesce(s.biz_no,'') <> '';

-- 4) 워시: 실제 세금계산서 발행 기록 (업체별 · 최근)
select shop, mode, ok, to_name, total, nts_no, at from wash_taxlog where mode = '실제' order by at desc limit 100;

-- 5) 워시: 알림톡으로 나간 것 중 우리 주소가 아닌 링크가 들어간 것
select shop, to_num, method, ok, left(body,200) as body, at from wash_sendlog
where upper(method) = 'ATA' and body ~* 'https?://' and body !~* 'https?://([a-z0-9-]+\.)*(cgg\.co\.kr|chagotgan\.co\.kr)'
order by at desc limit 100;

-- 6) 워시: 운영에서 카드 결제가 켜져 있는지 (꺼져 있으면 W-H3 해당 없음)
select pg_on from wash_hq where id = 1;
```
(2번은 첫 칸(보통 id) 차례로 최근 것부터 보여요.)

## ② 막는 SQL (흔적이 없을 때 · 서버 배포 없이 바로 막음 — 서버 방이 표 칸 이름 확인 후 실행)
- 생각: 사업자번호·팝빌 칸은 **처음 비어 있을 때만** 정할 수 있고, 한 번 정해지면 화면(서버의 대표 저장)으로는 못 바꾸게 DB 트리거로 막음. 바꿔야 하면 본사가 SQL 로(트리거를 잠깐 끄고). + 같은 번호를 두 곳이 못 쓰게 부분 유일 색인.
- 주의: 1·3번 확인에서 **이미 같은 번호를 쓰는 곳이 있으면** 유일 색인은 만들어지지 않으니, 그 줄부터 본사가 확인.
- 실제 SQL 문안은 서버 방이 칸 이름을 확인해 `서버/sql/` 에 «운영 급한 고침» 파일로 만들고 보안 방이 한 번 보고 대표님이 실행.

## 급한 고침 SQL 확인 — `서버/sql/급한고침_사업자번호_잠금.sql` (71ebc5b)
**통과 — 대표님 실행 OK.** (0번 확인이 «행 없음»일 때 파일 전체 실행)
- 잠금: `before update` 트리거가 이미 들어 있는 `biz_no`·`popbill_corp`·`popbill_userid`(체크) · `biz_no`·`pb_id`(워시)를 **예전 값으로 되돌림**(오류 없음 → 다른 설정 저장은 그대로). 풀림은 `current_user` 가 postgres/supabase_admin(SQL Editor)일 때만 — 서버는 service_role 이라 못 풂. 함수는 invoker(definer 면 잠금이 풀리므로 맞음).
- 트리거 차례: 이름 순서로 `wash_shops_biz_lock` → `wash_shops_not_hq_biz` (되돌린 뒤 본사 번호 확인) — 맞음.
- 빈 칸 처음 넣기 길(v21.2·v111)은 그대로 되지만, **유일 색인 4개**가 «이미 쓰는 번호»와 같으면 막음. 체크는 팝빌이 실제로 쓰는 번호(`popbill_corp` 없으면 `biz_no`) 기준이라, 빈 `popbill_corp` 를 남의 번호로 처음 채우는 길도 색인이 막음. 워시는 본사 번호도 막음.
- 기록: `biz_lock_log`(RLS·정책 없음) 에 시도한 칸·누구만 · 값은 안 남김 — 좋음.
- 남는 위험(서버 방도 적음): 아직 번호를 안 넣은 곳의 번호를 다른 곳이 먼저 넣는 것. 0번 확인·`biz_lock_log`로 보이고, sb15·v32 «본사 확인 뒤에만 발행»으로 막음.

## 고침 (금 18:00 ①-0 중) — 확인 SQL 4)·5) 시각 칸 이름
- 운영 `wash_taxlog`·`wash_sendlog` 의 시각 칸은 `created_at` 이 아니라 `at` (sb1 1066줄). 위 ① 4)·5) 를 `at` 으로 고침. 읽기만 하는 확인 SQL 이라 실패해도 바뀐 자료 없음.
