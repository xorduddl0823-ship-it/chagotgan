# 결제 세 가지 설계 초안 (결제 방, 2026-10-15)

> 상태: **초안**. 돈이 오가는 기능이라 **만들기 전에 보안 방 검토**(규칙 2-5)를 받아요. 법 해석은 법률 자문이 아니고, ①의 구조는 **토스페이먼츠 계약 담당 + (필요하면) 변호사·세무사 확인** 뒤 확정해요.
> 실제 코드: 서버는 서버 방, 화면은 각 제품 방. 결제 방은 설계서·요청서·시험 시나리오를 넘겨요. 시험은 **토스 테스트 모드만**.
> 지금 있는 것은 `02_지금_있는_것.md`.

| 원칙 | 내용 |

## ① 딜러앱 일괄 결제 (여러 업체 청구서를 한 번에)

### 상황
- 딜러(상사)는 워시·휠·리페어 등 **여러 업체**에 차를 맡기고, 업체마다 월말 청구서를 받아요.
- 지금은 업체마다 **계좌이체**. 딜러는 「한 번에 결제」를 원하고, 대표님은 「차곳간이 돈을 받아 나눠 주지 않기」로 정했어요.

### 법적으로 걸리는 부분 (요약)
- 금융위원회(2024-06-24 보도설명): 플랫폼이 **결제 대금 정산을 대행·매개**하면 **전자지급결제대행업(PG) 등록**이 필요해요(안 하면 3년 이하 징역 또는 2천만 원 이하 벌금). **다만 정산을 외부 PG사가 하고, 플랫폼은 입점사 계좌 정보 같은 정산에 필요한 정보만 주면 등록이 필요 없어요.**
  - https://fsc.go.kr/no010102/82523
  - https://www.korea.kr/news/policyNewsView.do?newsId=148930669
- 전자금융거래법 개정(2025-12-16 공포, **대부분 2026-12-17 시행 예정**): PG 정의 정비, 「PG로 등록한 자만 가맹점 계약 가능」 등. 시행 뒤 구조가 그대로 괜찮은지 다시 확인 필요.
  - 김·장 해설: https://www.kimchang.com/ko/insights/detail.kc?sch_section=4&idx=33494
  - 토스페이먼츠 블로그 「전자금융거래법 개정, 어떻게 대비해야 할까요?」: https://www.tosspayments.com/blog/articles/amendment

### 고를 수 있는 방식

> 「차곳간이 받아서 나눠 주는 안」은 **대표님 확정(결정 기록 2026-10-15)에 따라 비교에서 뺐어요.** 아래는 모두 **토스가 직접 각 업체에 돈을 보내는** 방식이에요.

| | A. **토스 지급대행** (추천) | B. 업체마다 각자 토스 가맹점 | B'. 하위몰(호스팅사형) 묶음 가입 | C. 계좌이체 유지 + 묶음 안내 |
|---|---|---|---|---|
| 토스가 직접 나눠 주나? | **예** — 결제는 한 번, 토스가 업체별 계좌로 지급(지급대행 API) | 예 — 업체별 결제라 각자 토스에서 받음 | 예 — 업체마다 토스 하위 가맹점(MID)이 생겨 각자 받음 | (토스 안 씀) |
| 딜러가 누르는 횟수 | **한 번** | 업체 수만큼(한 화면에서 차례로) | 업체 수만큼(한 화면에서 차례로) | 업체 수만큼 이체 |
| 업체마다 토스 가맹 필요? | **아니요** — 차곳간에 정산 계좌 등록 + 본인인증 문자 한 번 | **예** — 업체마다 가입·서류·카드사 심사(약 2주) | 예, 다만 차곳간이 대신 신청을 모아 줌(**토스가 이 방식을 차곳간에 열어 주는지 문의 필요**) | 아니요 |
| 차곳간 PG 등록 | 금융위 안내상 **불필요**(정산은 토스가 하고 차곳간은 계좌 정보만 줌) — 계약 때 확인 | 불필요 | 불필요 | 불필요 |
| 차곳간 토스 계약 | 기본 계약 + **지급대행 별도 계약·심사** | 없음(업체가 각자) | 호스팅사(플랫폼) 계약 | 없음 |
| 수수료 | 카드 수수료(토스 공시 일반 신용·체크카드 **3.4%**, 영세·중소 등급이면 우대) + **지급대행 수수료(공개 안 됨 → 문의)** | 업체마다 카드 수수료 + 가입비·연관리비(블로그상 가입비 22만·연 11만 원, **공식 확인 필요**) | 문의 | 이체 수수료만(딜러 부담) |
| 가입 절차·기간 | 차곳간: 토스 기본 계약(토스 1~2일 + 카드사 최대 14일) → 지급대행 계약. 업체: 셀러 등록 즉시(개인은 본인인증 뒤), **주 1천만 원 이상은 KYC 심사**(1년/3년마다 재심사) | 업체마다 약 2~3주 | 문의 | 없음 |
| 단점 | 차곳간이 카드 영수증상 판매처(중개자)로 보일 수 있어 세금 자료 정리 필요 | 작은 업체는 가입 안 할 가능성 큼 | 토스가 열어 줄지 불확실 | 편하지 않음 |

수수료 출처: 토스페이먼츠 PG 수수료 https://www.tosspayments.com/about/fee · 토스 FAQ(심사 1~2일, 카드사 최대 14일) https://docs.tosspayments.com/resources/faq · 지급대행 KYC https://docs.tosspayments.com/guides/v2/payouts · 가입비·연관리비(블로그) https://modumvp.com/guide/toss-payments-integration/ · PG 하위가맹점도 영세·중소 우대수수료 적용(금융위) https://www.fsc.go.kr/po010104/86274

**토스에 물어볼 것** (① 관련): 지급대행 수수료·최소 조건 / B2B 업무 서비스 청구서 대금에 지급대행을 쓸 수 있는지 / 하위몰(B') 방식을 열어 주는지 / 카드 전표의 판매처 이름이 업체로 찍히는지 차곳간으로 찍히는지

**토스 지급대행 요점** (공식 문서)
- 「오픈마켓 대신 토스페이먼츠가 셀러(입점 판매자)에게 대금 지급을 대행」하는 서비스. 셀러 등록 API → 사업자번호·계좌 검증 → 지급 요청(당일 `EXPRESS` / 날짜 지정 `SCHEDULED`) → 웹훅으로 결과.
- 개인·개인사업자 셀러는 본인인증 문자를 마쳐야 지급 가능, 법인은 등록 직후 가능. **주 1천만 원 이상**은 KYC 심사.
- 부가 API라 **별도 계약** 필요. 계약 문의: 1544-7772, support@tosspayments.com
- https://docs.tosspayments.com/guides/v2/payouts · https://docs.tosspayments.com/resources/glossary/payout · https://docs.tosspayments.com/reference/additional

### 추천: **C로 시작 → A로 넘어가기**
1. **지금(토스 계약 전)**: C. 딜러앱 「청구서」 메뉴에 업체별 청구서를 모아 보여 주고, 업체별 계좌·금액·「복사」 단추. 업체가 입금 확인(지금 `deposit_ok`)하면 딜러앱에서 「완료」로 바뀜. → 결제사 없이 바로 만들 수 있고 법 위험 없음.
2. **토스 기본 계약 + 지급대행 계약 뒤**: A. 딜러가 청구서 여러 장 체크 → 한 번 결제 → 서버가 업체별로 지급 요청.
3. 지급대행 심사가 안 되면: B를 「원하는 업체만」 선택 기능으로.

### A의 흐름 (만들 때)
```
딜러앱 [청구서] → 업체별 청구서 목록(이번 달, 금액, 상태) → 여러 장 체크 → [합계 ○원 결제]
  → dealer-api: 청구서들이 이 딜러 것인지·금액·상태를 서버가 확인 → 묶음 주문(pay_batch) + 업체별 줄(pay_batch_item) 만들기
  → 토스 v2 결제창(카드) → 돌아오면 서버가 승인(confirm) + 웹훅으로도 확인
  → 승인되면 각 청구서 «결제됨», 업체별 지급 요청(수수료 뺀 금액, 지급일)
  → 업체에 「입금 확인」과 같은 정보 알림톡, 딜러에게 결제 완료 알림톡
```
- **부분 취소**: 청구서 한 장만 취소하면 토스 부분 취소 + 그 업체 지급 취소/차감.
- **수수료**: 카드 수수료를 누가 내는지(업체 지급액에서 뺌 추천) → 대표님 결정거리.
- 딜러 로그인은 dealer-api 따로(통합 로그인 전환은 서버 방 일). 결제 기능은 **통합 로그인 전환 뒤** 붙이는 게 안전.

## ② 사용자 페이지 월 구독요금 — 한 번 결제

지금 워시 서버의 `payStart`·`payConfirm` 을 **그대로 살리고 빈 곳만 메워요.**

| 할 일 | 왜 | 누구 |
|---|---|---|
| 토스 **웹훅** 받는 곳 추가(결제 상태 변경) + 「결제 중(ready)」 30분 넘은 주문 다시 조회 | 결제 후 창을 닫아도 반영되게 | 서버 |
| 환불(`hqPgCancel`) 때 월 이용요금이면 `paid_until` 되돌리기, `wash_payments` 도 「환불」로 | 지금은 기간이 그대로 남음 | 서버 |
| 결제창 v1 → v2 | 토스 최신 방식, 정기 결제와 같은 SDK | 워시·체크 화면 방 |
| 「이번 달 냈나」 기준을 `paid_until` 하나로 | 달력 월 vs 30일 어긋남 | 서버 |
| 결제 장부 두 개 → 관리 「결제 내역」에서 합쳐 보기 | 대표님이 한 화면에서 보게 | 서버·관리 |
| 영수증: 카드는 토스 영수증 주소(`receipt.url`)를 결제 내역에 「영수증」 단추로 | 업체가 경비 처리 | 화면 |

- 부가세: 요금제 가격은 **부가세 별도**로 저장, 결제는 ×1.1 (지금 방식 유지).
- 캐시로 일부 결제: 지금처럼 유지.

## ③ 정기 구독 (자동 결제·빌링)

### 토스 자동결제 요점 (공식 문서)
- **리스크 검토 + 추가 계약 뒤** 사용 가능. **정기 구독형 서비스만** 허용.
- 흐름: 결제창으로 카드 등록·본인인증 → 서버가 **빌링키** 발급 → 결제일마다 서버가 빌링키로 승인 요청(일정은 우리가 직접 돌림).
- 빌링키는 **다시 조회 불가** → 발급 때 서버에 안전하게 저장. `customerKey` 는 겹치지 않는 값.
- 카드 재발급·한도 초과·만료 등으로 실패할 수 있음 → 재시도 필요.
- https://docs.tosspayments.com/guides/v2/billing · https://docs.tosspayments.com/guides/v2/billing/integration · https://docs.tosspayments.com/resources/glossary/billing

### 법: 정기결제 고지 (전자상거래법 개정, 2025-02-14 시행)
- 「숨은 갱신」 금지: 무료 체험 → 유료 전환, 정기결제 금액 인상은 **미리 알리고 동의**를 받아야 해요(기간 등은 시행령). 차곳간 손님은 업체(B2B)라 적용 범위가 다를 수 있지만 **그대로 지키는 쪽**으로 설계.
- https://www.newsis.com/view/NISX20250213_0003063585 (공정위 문답 정리)
- 이미 정한 방향(2026-10-14 체험판 결제 유도)과 연결: 체험 끝 → **자동 전환하지 않고**, 업체가 직접 「자동 결제 켜기」를 눌러야 시작.

### 흐름
```
[가입·등록]
업체 대표가 [자동 결제 켜기] → 동의 화면(금액·결제일·해지 방법·첫 결제일) → 토스 v2 카드 등록창
  → 서버: authKey 로 빌링키 발급 → 저장(비밀 칸, 화면으로 절대 안 내려감) → 카드 끝 4자리·카드사만 화면에 표시

[결제일] (매일 아침 서버가 한 번 돌림, 수파베이스 예약 실행)
paid_until 이 오늘인 자동결제 업체 → 서버가 금액 계산(요금제 ×1.1 − 쓸 캐시) → 빌링 승인
  성공 → 지금 payDone 그대로(+30일, 결제완료 알림톡)
  실패 → 「결제가 되지 않았어요」 정보 알림톡(사유: 한도·만료 등, 버튼 없음) → 재시도
         (템플릿 「차곳간_자동결제실패」(알림톡/02 F) 변수: 업체명 · 결제일 · 요금제 · 금액 · 사유 · 다음시도일. D+1·D+3 실패에 보내고, D+5(마지막) 실패에는 기존 잠금 안내)

[재시도 · 이용 제한] (지금 잠금 장치 재사용)
  D+1, D+3 재시도 → D+5 마지막 재시도
  그동안은 「잠금 전 유예」(지금 lock_days 7일과 맞춤) → 그래도 실패면 기존 잠금 → 막힘 → 90일 뒤 자료 정리
  업체가 카드 바꾸면 그 자리에서 바로 한 번 승인

[해지]
언제든 [자동 결제 끄기] → 이번 기간 끝까지 사용, 다음 결제 없음. 빌링키 삭제.

[금액 변경]
요금제 인상 → 정해진 기간 전에 알림톡으로 알리고 동의 받기. 동의 안 하면 자동 결제 멈춤(기존 가격 기간 끝까지).
```

### 새로 필요한 자료 (서버 방에 요청할 표 초안)

## 시험 시나리오 (토스 테스트 모드)
1. 월 요금 카드 결제 성공 → +30일, 알림톡 1번, 장부 1줄
2. 결제창에서 결제 후 창 닫기 → 웹훅으로 반영되는지
3. 같은 주문 승인 두 번(새로고침) → 한 번만 반영
4. 화면에서 금액 바꿔 보내기 → 거절
5. 매니저·직원 계정으로 결제 시도 → 거절(대표만)
6. 자동 결제 등록 → 결제일에 승인 → 성공
7. 테스트 카드로 실패 → 재시도 D+1·D+3·D+5 → 잠금으로 넘어가는지
8. 자동 결제 끄기 → 다음 결제 안 됨, 빌링키 삭제
9. 월 요금 환불 → 기간 줄어드는지
10. (①) 청구서 3장 한 번 결제 → 업체별 지급 요청 3건, 1장 부분 취소

## 보안 방 검토 결과 반영 (2026-10-15, `보안/검사기록/2026-10-15_결제설계_검토.md`)
판정: **방향은 좋음.** 아래를 설계에 넣었어요. 서버 방은 만들 때 이대로 해요.

**먼저 고칠 것 (높음, 웹훅·카드 켜기 전에)**: 지금 `payConfirm` 은 같은 주문이 동시에 두 번 오면 이용기간이 +60일이 될 수 있고, 두 번째 승인 오류가 주문을 `failed` 로 덮어쓸 수 있어요.
→ `ready → confirming`(한 번에, 바뀐 줄이 있을 때만 진행) → 토스 승인 → `confirming → paid`(바뀐 때만 `payDone`). 승인 오류면 토스 조회로 실제 상태 확인 뒤 기록. **웹훅도 같은 함수**로.

| 항목 | 설계에 넣은 것 |
|---|---|
| 빌링키 | AES-GCM, 줄마다 무작위 IV, **열쇠 판 번호 칸**(`PAY_ENC_KEY` 교체 대비). 토스 발급 응답은 **빌링키를 뺀 뒤** 저장(`raw` 통째 저장 금지). `customerKey` 는 서버 무작위 값, 카드 등록창 열기 **전에** 업체 몫으로 저장하고 돌아올 때 같은 업체인지 확인. 끌 때 우리 표 삭제 + 토스 삭제 기능 호출. `pay_billing` 은 RLS 켜고 정책 없음(서버만) |
| 웹훅 | 주문번호만 믿고 상태·금액은 토스 조회로, **조회 금액 = 주문 금액일 때만** 반영. 모르는 주문은 기록만. 200 먼저, 무거운 일은 뒤에. 결제 전용 함수 `pay-hook` |
| 금액 | 서버 계산 유지. 캐시 일부 사용은 **승인 성공 뒤에만** 깎기 |
| 권한 | 결제·자동결제 켜기/끄기·카드 바꾸기 `ownerOnly`, 환불 `hqOnly`. **자동 결제 켜기·카드 바꾸기 때 업체 대표 번호로 정보성 알림톡** |
| 두 번 청구 | 「업체+결제일」 주문 줄을 unique 로 먼저 만들고 성공한 실행만 청구. 토스 요청에 **같은 주문번호 + 멱등 키(Idempotency-Key)**. 재시도 D+1·3·5는 같은 기간 주문을 이어 씀. 청구 전 `paid_until` 이 이미 늘었는지 다시 확인 |
| 딜러 청구서 | **받은 휴대폰 번호 = 딜러 로그인 번호**로만 잇기(이름 금지, 청구서 만들 때 받는 번호 저장). 보여 줄 것: 업체명·월·대수·금액·입금 기한·**청구서 만들 때 찍어 둔 계좌**·상태·보기 주소. 업체 설정 계좌가 바뀌면 「계좌가 바뀌었어요」 표시. 업체 대표 전화·다른 딜러 정보는 안 보냄. 업체 화면에 「받는 번호 확인」 안내 |
| 실패 알림톡 | 템플릿 「차곳간_자동결제실패」(알림톡/02 F) 변수: 업체명 · 결제일 · 요금제 · 금액 · 사유 · 다음시도일. D+1·D+3 실패에 보내고, D+5(마지막) 실패에는 기존 잠금 안내. 정보성·버튼 없음. 사유는 「한도 초과·카드 만료」 정도, 토스 오류 원문·카드 번호 금지(끝 4자리까지) |
| 비밀값 | `PAY_CLIENT_KEY` 는 공개 키(화면에 나가도 됨). 나머지는 서버 비밀값만. 테스트·실제 열쇠를 구분해 화면에 「테스트 모드」 표시 |
| 환불 | `paid_until` 은 **환불한 날수만큼 빼기**(예전 값으로 되돌리면 다음 달 결제분까지 사라짐). 오늘·다른 결제가 끝나는 날보다 앞으로 안 감. `paid → refunding → refunded` 한 번에 바꾸기로 두 번 환불 막기, 부분 환불 합계 ≤ 결제 금액 |
| 그 밖 | 홈페이지 가입 결제(로그인 전)를 켤 때는 따로 다시 검토 |

### 서버 구현 보안 검사 결과 (2026-10-15, 워시 sb10 · pay-hook · 딜러 d6 · SQL 06 통과)
설계 검토 6항목 모두 반영 확인. **자동 결제 스위치 `billing_on` 을 켜기 전에** 서버 방이 아래 2개를 고쳐야 해요(보안 판정: 중간).
1. **토스 요청이 끊기거나 시간이 넘으면 「실패」로 단정하지 않기** — 실제로는 결제됐을 수 있어요(돈은 나갔는데 이용기간이 안 늘어나는 상태). 예외면 주문을 `ready` 로 두고 정리 예약이 다시 묻게 하거나, 정리 예약이 최근 3일 자동 결제 `failed` 주문도 토스에 다시 묻게 하기.
2. **가짜 웹훅이 몰려도 진짜 웹훅이 밀리지 않게 하기** — 지금 `pay-hook → payCheck` 가 하루 제한을 한 줄로 같이 써요. `pay-hook` 이 내부 열쇠(`CGG_INTERNAL_KEY`, 이름만)를 붙여 부르고 `payCheck` 는 제한을 따로 세기 + `pay-hook` 에 요청 IP별 제한.
- 참고(낮음): 전액 환불이면 이용기간이 오늘보다 앞으로 갈 수 있음(의도한 동작) · 부분 환불은 한 주문에 한 번만(안전한 쪽) · 토스 빌링키 삭제 API 경로는 테스트 모드에서 확인.
- 기록: `보안/검사기록/2026-10-15_결제설계_검토.md` 맨 아래
- ✅ 서버 방이 조건 2개 반영 완료(2026-10-15). `bill_fail` 사유는 짧은 말 5가지(잔액 부족·카드 한도 초과·카드 유효기간 지남·카드사 승인 거절·카드사 사정), 토스 원문 없음, D+5 마지막 실패엔 안 보냄(잠금 안내). `bill_on` 변수는 알림톡 방이 정하면 맞춤.
