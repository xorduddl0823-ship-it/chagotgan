# 출시마감 3차 — 챗지피티 2차 검수 반영 (대표님 «검토 후 진행» 10/19)

근거: `운영/긴급/챗지피티_검수_출시마감_2차결과.md`. 시험기(28개 · 미실행 끝 코드 2)는 **완료 처리**, 다시 손대지 않음.
범위는 아래 두 코드 수정 + 마감 자료뿐. 디자인·통합 로그인·다점포·새 기능 금지. 운영 변경·배포·실제 고객 발송 금지.

## [1] 워시 화면 ↔ 서버 발송 키 하나로 (P1) — 서버 방 + 워시 방
- 약속: **본문 최상위 `rid`(소문자·숫자 24자)** 하나로 통일. 워시 v142의 `sendKey`는 rid로 바꿈(서버가 sendKey를 따로 받지 않음).
- 같은 발송 재시도 = 같은 rid, 사용자가 일부러 «다시 보내기» = 새 rid.
- 알림톡 → 문자 대체는 한 발송 업무(한 rid) 안에서 처리.

## [2] 발송 경로 멱등 실패 처리 (P1) — 서버 방 (워시·체크 둘 다)
- cgg_idem insert가 23505 말고 다른 오류면 `run()`으로 우회 금지 → 공급자 호출 없이 «잠시 뒤 다시» 안내.
- done 업데이트 error 확인. 실패하면 «확인 중».
- 공급자 접수 뒤 응답 유실 · 완료 기록 실패 · 타임아웃 = «확인 중»(결과 불명). «보내지 못함 확정»과 구분.
- run 행을 5분 뒤 지우거나 catch에서 무조건 지워 자동 재발송 금지. 확인 중이면 자동 재발송 막고 화면에 «확인 중 — 보낸 기록에서 확인» 표시(공급자 결과 조회가 되면 조회로 정리).
- 오래된 작업 재획득은 조건부 원자적 변경 한 번(읽기→삭제→넣기 금지).
- 기록 저장(upsert)은 지금 정책 유지 가능. 외부 부작용(발송)만 위 규칙.

## 필수 시험 (핵심만)
1. 정상 반복 · 동시 클릭 → 공급자 접수 1회
2. DB claim 오류 → 공급자 접수 0회
3. 접수 뒤 응답 유실 / 완료 저장 실패 → 다시 해도 추가 접수 0회
4. 실제 미접수 확정 실패 → 안전하게 다시 가능
5. 기록 저장 실패와 발송 실패를 각각 표시, 저장 성공 기록은 발송 실패로 없어지지 않음
6. 다른 업체 차량·청구서·사진 접근 차단(A/B 28)

## 제출 (diff만 말고 «명령 한 번으로 돌아가는» 묶음)
- 워시·체크 화면/서버 전체, 기사 앱, A/B에 필요한 딜러 서버 전체 파일
- 가짜 DB 모듈 · import map · 미리보기 생성기 또는 완성 시험 페이지 · 실행 명령(README 한 줄)
- 비밀키·고객 자료 없는 시험 데이터와 실제 실행 결과
- 단일 적용 순서 한 장: ① 상태 확인(읽기) → ② 기존 중복 보호·백업/되돌리기 확인 → ③ SQL 24 · **26** → ④ 서버 sb29(가칭)/v54 → ⑤ 대응 화면(워시 새 판 · 체크 v56.6 · 기사 v29) → ⑥ 지정 시험 업체 점검(저장→재로그인, 한 번 발송→결과 조회→다시 하기 막힘)
- 알림별 «승인 / 설정 / 실수신»을 확인됨·미확인으로 분리(알림톡 방). 체크 재검사 자동 알림톡은 승인 확인 전 «차단».
