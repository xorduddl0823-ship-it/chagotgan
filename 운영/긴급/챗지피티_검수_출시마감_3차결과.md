## 판정

**지난 2차의 두 코드 문제는 해결 확인. 이번 직접 검사에서 새 출시 차단 코드 결함은 발견하지 못했습니다. 코드 검수는 마감하고 운영 적용 확인·지정 번호 실수신 단계로 넘어가도 됩니다.**

현재 파일 기준 판:
- 워시 화면 v143.1 / 서버 sb29
- 체크 화면 v56.9 / 서버 v54

‘운영에서 지금 즉시 사용 가능’까지 확인했다는 뜻은 아닙니다. 운영 DB와 설정·배포 버전은 확인하지 않았고, 실제 알림톡을 발송하거나 수신하지 않았습니다. 이번 결과를 배포 실행 승인으로 해석하지 마세요.

| 워시 sendKey와 서버 rid 불일치 | 해결 | 워시 GS.send가 본문 최상위에 유효한 rid를 넣고 같은 발송의 재시도에 같은 키를 전달. PC·모바일 브라우저에서 요청 payload 확인 |

## 시험 환경 보정 — 제품 코드는 변경하지 않음

실행에 필요한 다음 조정은 별도 시험 사본에만 적용했습니다.

1. 시험 사업자번호 `87612XXXXX`, `876-12-0XXXX`가 숫자 10자리 검증에서 막혔습니다. 둘을 같은 시험 전용 숫자 `1234567890`, `123-45-67890`으로 치환한 뒤 정상 통과했습니다. 이는 제품의 중복 차단 실패가 아니라 마스킹된 시험 자료의 형식 문제입니다.
2. 격리 A/B 실행기가 옛 저장소 경로를 가리켜, 제공된 `AB_FILE` 환경변수로 묶음 안 시험기를 지정했습니다.
3. 외부 JSR 의존성을 내려받을 수 없어, 시험 import map에서 표준 crypto/base64 모듈만 로컬 Node 구현으로 연결했습니다. 업체 권한·저장·발송·멱등 함수는 변경하지 않았습니다. 해당 외부 라이브러리 자체나 실서비스 배포 환경까지 검증한 결과는 아닙니다.
4. Chromium 실행 경로를 현재 환경에 맞췄습니다. 워시 브라우저 검사에는 시험 사본의 닫힌 함수 범위에서 기존 함수를 호출할 수 있는 노출 지점만 추가했습니다. 함수의 업무 로직은 변경하지 않았습니다.

업로드 원본 zip과 운영 코드·자료는 변경하지 않았습니다. 실제 고객에게 보낸 메시지는 0건입니다.

## 남은 운영 마감 — 추가 기능 개발 아님

### 1. 운영 상태와 적용 결과 확인

승인된 담당자가 동봉 적용 순서에 따라 읽기 전용 상태 확인 → 백업 확인 → SQL 24 및 **26 3차판** → 대응 서버 → 대응 화면 순으로 진행하고 결과를 확인해야 합니다.

필수 확인:
- SQL 26의 표·4개 상태 제약·RLS 활성화
- 사업자번호 중복 차단 제약과 기존 중복 보호 상태
- 사진 저장소 비공개·업체 접근 정책
- 레거시 접근이 허용되지 않는지 확인. 비밀값의 존재 여부만으로 활성 여부를 확정하지 말고, 담당자가 서버 판의 실제 판정 조건까지 확인하되 값은 대화에 공개하지 않기
- 서버 실제 응답 판 sb29/v54 및 화면 v143.1/v56.9/기사 v31

기존 중복 자료의 병합·삭제는 이번 검수 마감 조건으로 추가하지 않습니다. 별도 승인·계획을 따르세요.

### 2. 지정 번호 실수신 1회 확인

사용자가 허용한 시험 업체·시험 수신번호·알림 종류에 한해 확인합니다. 승인 전에는 실제로 보내지 않습니다.

각 제품에서 실제 사용할 흐름만 골라:
- 기록 저장 → 로그아웃·재로그인 → 원래 값 유지
- 알림 1회 → 실제 휴대전화 도착·수신자·차량·금액·링크 확인
- 같은 업무의 통신 재시도 → 추가 접수/중복 메시지 없음
- 보낸 기록의 접수·전달·실패·확인 중 상태 구분

화면의 의도적인 ‘다시 보내기’는 새 rid이므로 새 발송입니다. 이를 단순히 눌러 놓고 ‘중복 방지 실패’로 판정하면 안 됩니다. 동일 업무 재시도 시험과 의도한 재발송을 구분하세요.

### 3. 체크 재검사 알림

승인된 템플릿과 채널 설정이 확인되기 전까지 자동 알림톡은 열지 않습니다. v54의 미설정 자동 차단은 시험에서 통과했습니다. 수동 문자 운영 여부와 비용은 사용자가 결정해야 하며, 이번 검수에서 자동으로 허용하지 않았습니다. 다른 통과 기능의 출시까지 이 기능 때문에 모두 보류할 필요는 없습니다.

### ‘확인 중’일 때의 운영 안내

‘내 휴대전화에 아직 안 왔다’만으로 미접수가 확정된 것은 아닙니다. 공급자 기록에서 거절·미접수 확정 또는 기존 발송의 종료 상태를 확인한 뒤 의도적 재발송을 판단하세요. 확인 중인 업무를 새 키로 재발송하면 기존 발송까지 도착해 중복될 수 있습니다. 현재 자동 결과 정리 기능은 후속 개선으로 남겨도 되지만, 이 안내는 운영자가 알아야 합니다.
