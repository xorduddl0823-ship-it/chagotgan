## 판정: 보완 후 재검증 필요

이번 묶음은 정책안과 1차 정적 조사 자료입니다. 수정된 서버 원본·DB 마이그레이션·실제 A/B 시험 결과·운영 읽기 전용 조사 결과는 없습니다. 따라서 ‘수정 완료’, ‘유출 없음’, ‘운영 안전’ 판정은 할 수 없습니다.

보고서의 ‘각자 다른 업체의 대표이며 사업자번호로 자동 연결되지 않는다’는 설명은 가능한 구조입니다. 그러나 첨부된 서버 원본이 없어 독립적으로 재확인하지 못했습니다. P1은 보고서에 따른 잠정 분류로만 유지해야 합니다. 실제 다른 업체 자료 접근이 확인되면 P0로 올립니다. 이번 검수에서 실제 유출은 확인하지 않았습니다.

제가 직접 확인한 결함은 A/B 시험의 판정 오류입니다. 네트워크를 전혀 호출하지 않고 fetch를 가짜 응답으로 대체한 로컬 실행에서, 정보 노출·삭제 성공을 나타내는 응답이 있어도 16/16 통과했습니다. 모든 시험을 건너뛰어도 종료 코드가 0이었습니다. 이 시험 결과로 보안 완료를 선언하면 안 됩니다.

운영 API·DB·실제 고객 자료는 열거나 변경하지 않았습니다. 업로드 원본도 수정하지 않았습니다.

### B01 — 시험 판정 오류: 직접 재현

첨부 `AB_시험_업체격리.js`를 Node vm에서 실행하고 fetch를 메모리 함수로 바꿨습니다. 가짜 토큰·가짜 업체·가짜 자료만 사용했습니다. 실제 서버 요청은 0건입니다.

| 시험 | 가짜 응답 | 실제 판정 | 잘못된 이유 |
|---|---|---|---|
| W4 사진 서명 주소 | `{links:['MOCK_OTHER_TENANT_URL']}` | 통과 | `j.result.links`가 없으면 undefined를 빈 목록으로 취급 |
| C3 타 업체 청구서 | `{rows:[{id:'FAKE_INV',mock:'OTHER_TENANT_DATA'}]}` | 통과 | rows가 있어도 `empty(j.result)`가 true라 OR 조건 통과 |
| C4 타 업체 청구서 삭제 | `{result:{deleted:1}}` | 통과 | 최상위 삭제 수가 없으면 0으로 간주 |
| W0/C0 자기 자료 대조 | `{}` | 통과 | 오류가 아니라는 것만 확인하고 실제 대상·소속·데이터 존재는 확인하지 않음 |
| C6 삭제 후 원본 대조 | 청구서 내용 임의 변경 응답 | 기존 코드로는 미탐지 가능 | 오류 유무만 보므로 삭제·변조 전후 동일성 보장 안 됨 |

가짜 응답 전체 실행 결과: ‘모두 16 · 통과 16 · 실패 0 · 건너뜀 0’, 종료 코드 0.
필수 입력을 모두 생략한 별도 실행: ‘모두 16 · 통과 0 · 실패 0 · 건너뜀 16’, 종료 코드 0.

이 응답들이 실제 서버의 반환 형식이라고 주장하는 것은 아닙니다. 서버별 확정 응답 형식이 첨부되지 않았고, 예상하지 않은 형식·누락 필드를 거절하지 않는 시험기 결함을 확인한 것입니다.

**수정 원칙:** 실제 API 계약에 맞는 디코더를 먼저 적용합니다. 스키마 불일치·필드 누락·5xx·응답 해석 실패는 시험 실패입니다. 거절 시험은 명시한 권한/미존재 오류만 허용합니다. 빈 목록이 정상 응답인 API는 ‘목록 필드가 실제로 존재하는 배열’이고 길이 0일 때만 허용합니다. 대조군은 미리 만든 특정 시험 행을 실제로 조회해야 합니다. 삭제·변경 시험 전후에는 A 자료 내용과 개수·관계가 같은지 확인합니다.

## 2. 정책 질문 4개에 대한 답

### Q1. 사업자번호 + 종사업장번호면 모든 경우에 충분한가?

조건부로 사용할 수 있는 외부 식별 정보입니다. 서비스 내부의 변하지 않는 업체 ID로 사용하지 마세요. 별도의 불변 tenant_id를 두고 사업자등록 식별 정보와 관계를 맺어야 합니다. 사업자 정보 정정·제품 추가·사업장 변경으로 자료 소속이 바뀌면 안 됩니다.

국세청은 일반적으로 사업장별 등록, 사업자단위과세는 예외 구조로 설명합니다. 따라서 ‘같은 대표면 같은 업체’, ‘모든 지점에는 같은 번호’, ‘누구나 임의의 4자리 번호를 넣어 새 업체 생성’으로 단순화하면 안 됩니다. 이 자료만으로 법인·개인 다점포의 모든 세무 경우를 포괄했다고 인증할 수 없습니다. 증빙의 실제 식별 정보에 맞춰 처리해야 합니다.

정책에 다음을 명시하세요.
- 등록번호 미확정은 별도 상태로 관리하고, 기본값 0000을 넣었다는 사실이 본점·소유 확인을 뜻하지 않게 합니다.
- 동일한 기본 사업자번호가 이미 있으면 종사업장번호가 달라도 추가 사업장 검증·승인을 요구합니다. 임의 0001/0002로 승인 우회하면 안 됩니다.
- 번호 중복 승인 시 기존 업체 참여, 새 사업장 생성, 기존 업체에 제품 추가 중 어느 작업인지 구분합니다. 승인했다고 같은 키의 별도 업체를 만들지 않습니다.
- 워시·체크를 함께 쓰는 업체는 공통 tenant_id의 제품 이용 권한을 추가합니다. 로그인 멤버십은 user_id↔tenant_id↔role 관계로 관리합니다.
- 현재 보고서는 워시 전화번호 하나에 업체 하나만 가능하다고 설명하지만, 새 정책은 계정 하나로 여러 가게를 선택합니다. 기존 구조와 목표 구조의 충돌을 해소할 데이터 모델·마이그레이션이 필요합니다.
- 서로 다른 워시·체크 테이블의 개별 UNIQUE 인덱스만으로 전 제품 간 중복은 막지 못합니다. 공통 등록 원장과 그 고유 제약 등으로 경쟁 상태를 막고, 두 제품 활성화는 동일 업체의 관계로 표현합니다.

### Q2. 남의 번호를 먼저 등록하는 선점은?

‘처음 번호는 바로 사용, 겹칠 때만 승인’만으로는 소유권이 검증되지 않습니다. 국세청 API는 사업자 정보 일치와 운영 상태를 확인하는 서비스입니다. 그 결과만으로 신청자가 해당 업체의 대표·위임받은 직원이라는 사실이 증명되지는 않습니다.

가입 자체와 사업자 확인을 분리하세요. 미확인 상태에서 자기만의 시험 공간을 쓰게 할 수는 있지만, 검증된 업체 표시·세금계산서 발행 주체 확정·기존 자료 연결·외부 통지·결제 수취 정보 확정 등은 별도 권한 검증이 필요합니다. 제품 정책에 맞춰 위험 기능 범위를 명시하세요.

번호만 입력한 신청이 사업자번호를 영구 선점하지 않도록 미확인 신청 만료·요청 제한·이의 제기·본사 정정 절차가 필요합니다. 본사 승인은 증빙과 담당자·사유·시각·조치 종류를 기록하고, 신청자의 자기 승인이 불가능해야 합니다. 존재 여부 안내에는 기존 고객의 이름·전화·거래 정보를 공개하지 마세요.

### Q3. 통합 로그인 넘김 코드에서 빠진 조건은?

‘한 번짜리·짧은 시간’만으로 충분하지 않습니다.
- 예측 불가능한 코드, 서버 저장 시 해시, 짧은 만료, DB에서 원자적 1회 소비. 동시 교환 한 건만 성공.
- user_id·tenant_id·허용 역할·목적 제품·대상 수신 서버/정확한 콜백 주소·인증 시도와 연결. 요청자의 임의 업체 ID로 재발급 금지.
- 목적 제품에서 교환 시 현재 멤버십·활성 상태·제품 이용권·세션 철회를 재검증.
- 브라우저 로그인 시도와 state/nonce, PKCE S256 등 검증된 OAuth/OIDC 방식으로 연결하여 탈취·로그인 CSRF·코드 주입 방지. 다른 브라우저/제품/콜백에서 교환 거절.
- HTTPS, 정확한 redirect 허용 목록, 오픈 리다이렉트 금지. 코드·토큰을 로그·분석·Referer에 남기지 않기. URL에서 즉시 제거, no-store 등 적용.
- 목적 서버가 새 세션 발급. 브라우저 저장소에 장기 세션 토큰을 URL로 전달하지 않기. 본사 로그인·권한 상승은 일반 업체 코드로 대체 불가.
- 원 계정 로그아웃·퇴사·권한 변경·휴면·번호 재할당 시 기존 세션과 넘김 코드 처리 규칙 명시.

가능하면 새 자체 인증 프로토콜보다 검증된 OAuth/OIDC 구현을 사용하세요. 이는 제안이며 현재 파일에 구현됐다는 뜻은 아닙니다.

### Q4. 18개 점검표에서 빠진 경로는?

정적 JS는 워시 11 + 체크 5 + 딜러 2 = 18개입니다. 보고서의 G1·P1·S1은 이 자동 검사에 포함되지 않습니다. A/B JS는 설명의 15개가 아니라 실제 16개이며, cgg-api·dealer-api·pay-hook 동적 검사는 없습니다.

추가해야 할 주요 범위:
- DB 직접 REST/RPC·RLS·Storage 정책과 공개 버킷. API에서만 막아도 직접 경로가 열려 있으면 불충분.
- 공개 v/r/d 보기 링크의 대상·최소 공개 필드·만료·철회·추측 방지. 공개 링크의 정상 공유와 무단 접근을 구분.
- 사진/파일의 업로드·교체·삭제·서명 URL 재발급 및 경로 조작. 다운로드만 확인해서는 부족.
- 목록·검색·건수·엑셀·백업·일괄 처리·페이지네이션·복구·외부 연동의 업체 필터.
- 대표/직원/기사/딜러/본사 역할별 읽기·쓰기 차이, 퇴사·비활성 계정·기존 세션.
- 초대·승인·거절·대표 이전·가게 선택·비밀번호 재설정·OTP·전화번호 변경 경로.
- 가입·사업자 정보 변경·엑셀·본사 관리·동시 요청에서 동일 제약과 감사 기록.
- 결제 웹훅 중복·재전송·서명/서버 조회·주문과 업체 귀속. 결제 성공 여부 확인만으로 소속 분리 검증 완료 아님.
- 캐시·로그·실시간 구독·배경 작업·메시지/파일 수신자에도 업체 경계 유지.

## 3. 정적 검사·SQL의 한계

정적 JS는 문자열·정규식 검사입니다. `hqOnly` 문자열이 있다는 사실은 모든 실행 경로에서 먼저 실행된다는 증명이 아닙니다. 함수 추출 형식이 바뀌어 hq 함수가 0개 잡혀도 ‘누락 0개’로 통과할 수 있습니다. 체크 검사는 이름이 `id`라는 이유로 일부 쿼리를 제외하므로, 실제로 앞에서 검증한 ID인지 데이터 흐름을 보장하지 않습니다. 파싱 수·함수 범위가 기대와 다르면 실패시키고 원본 코드 리뷰와 실행 검증을 병행해야 합니다.

읽기 전용 SQL은 조사 보조 도구입니다. 0건이라는 결과가 과거 유출 부재를 증명하지 않습니다. 타 업체 자료를 조회만 했다면 FK·폴더 불일치가 없을 수 있고, 접근 로그가 없으면 과거 여부를 확정하기 어렵습니다.
- 주석의 ‘②~⑨ 0이면 정상’은 잘못됐습니다. ②는 계정 집계로 정상 계정도 행이 나오며, ⑧은 필요한 인덱스가 존재해야 하고, ⑨는 감사 기록이 있을 수 있습니다.
- ⑦의 설명에는 청구서 줄↔청구서 검사가 있지만 실제 쿼리에 해당 JOIN이 없습니다.
- ⑧은 인덱스 이름/존재만 조회합니다. UNIQUE 여부·정규화 식·WHERE 조건·종사업장 범위·유효 상태·전 제품 간 경쟁 방지까지 확인하지 않습니다.
- ⑨는 ‘겹친 업체만’이라는 설명과 달리 전체 최근 bizOk/bizUndo 기록입니다. 조건과 출력 마스킹을 맞추세요.
- ③·⑥은 고아 세션·비활성 사용자·만료 세션·전화번호 형식 차이까지 판정하지 않습니다. 의미별로 결과를 나누세요.
- 이름·업체 코드가 남는 SQL이 있으므로 결과를 외부에 전달할 때는 별도로 가리세요. 최초 요청서에는 실제 식별 정보가 남아 있어 묶음 전체가 비식별화됐다고 말할 수 없습니다.

## 4. 2차 제출 요청 / Claude Code 작업 지시서

```text
중복 사업자번호 1차 묶음 검토 결과: 정책·조사 단계이며 보안 수정 완료로 승인하지 않습니다.
실제 유출은 확인되지 않았고, 보고서의 P1은 잠정 판정입니다.
운영 데이터 삭제·병합·수정, 실제 고객 자료 교차 열람, 발송·결제·배포를 하지 마세요.
아래 작업은 격리된 시험 환경과 코드에서 진행하세요.

1. A/B 시험 판정부터 고치세요.
- C3의 empty(j.rows) OR empty(j.result), C4의 누락 삭제 수=0,
  W4의 누락 links=빈 목록, 대조군의 단순 !isErr 판정을 제거하세요.
- 실제 API별 확정 응답 스키마를 선언하고, 모르는 형식·누락·5xx는 실패시키세요.
- 권한 거절의 허용 오류 코드를 명시하고, 오류에 민감 자료가 섞여 있지 않은지도 보세요.
- 필수 값 누락·필수 시험 건너뜀은 비정상 종료하세요.
- A 시험 행의 존재와 B의 소속을 대조하고, A 원본을 전후 비교하세요.
- 잘못된 통과를 막는 시험기 자체 테스트에 아래를 포함하세요:
  {rows:[{id:'FAKE_INV'}]}, {result:{deleted:1}}, {links:['MOCK_URL']}, {},
  응답 해석 실패, 500, 전부 건너뜀. 이들은 안전 통과의 근거가 될 수 없습니다.
- 로그에 응답 본문·토큰·서명 URL·개인정보를 그대로 쓰지 마세요.
- 시험 환경 식별자를 검증하세요. AB_OK 문자열만으로 시험 환경이 보장되지는 않습니다.

2. 실제 수정 전후 diff와 DB 마이그레이션을 제출하세요.
- hqShopSave 포함 모든 등록/변경 경로의 정규화·중복·권한·감사 기록.
- 기사 회사 비밀번호의 중복 검사소 선택 금지.
- 기본 사업자번호가 같으면 임의 종사업장번호로 승인 우회 불가.
- 공통 사업자 원장/불변 tenant_id/제품 권한/다중 업체 멤버십 모델 명시.
- 동시 등록·변경 경쟁 시 한 건만 성공하는 DB 제약과 트랜잭션 시험.
- 미확인 사업자 신청이 영구 소유권/선점 권한이 되지 않는 정책.
- 대표 권한을 사업자번호 입력만으로 얻거나 이전할 수 없어야 합니다.

3. 통합 로그인 넘김 코드 보안 명세와 테스트를 제출하세요.
- 사용자·업체·역할·제품·대상·로그인 시도 바인딩,
  1회 원자적 교환·만료·재사용/동시 교환 거절·PKCE/state 등.
- 교환 시 현재 소속·역할·제품 권한을 다시 검증하세요.

4. 검증 범위를 확대하세요.
- 워시/체크뿐 아니라 딜러/cgg-api/본사/웹훅,
  DB RLS·직접 REST/RPC·공개 Storage·보기 링크·업로드/삭제·엑셀/백업.
- 대표/직원/기사/딜러/본사·퇴사/권한 철회별 A/B 접근 시험.
- 수정된 SQL에 청구서 줄 소속 검사와 실제 인덱스 정의·정책 검사를 추가하세요.
- SQL 0건을 과거 유출 없음의 증명으로 보고하지 마세요.

2차 묶음에는 다음을 포함하세요:
- 서버 원본 또는 검토 가능한 변경 diff와 커밋 식별자
- DB 스키마/마이그레이션과 환경별 적용 여부(미적용은 명시)
- 보정된 시험기와 시험기 자체 테스트 결과
- 격리 환경의 실제 A/B 시험 결과: 필수 실행 수·통과·실패·건너뜀
- 운영 판/ALLOW_LEGACY_KEY/Storage 공개 여부의 읽기 전용 확인 결과
  (접근 권한이 없으면 미확인으로 남기세요)
- 기존 중복 두 업체의 마스킹된 관계 조사와 정리 제안만 제출. 실행 금지.

모든 필수 경로가 통과하기 전에는 ‘유출 없음/보안 완료’라고 결론내리지 마세요.
```
