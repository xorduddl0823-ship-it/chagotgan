검수일: 2026-10-19 (한국 시간)

## 결론

**현재 묶음만으로 운영 사용 가능 판정은 아직 못 합니다. 추가 개발은 아래 두 가지로 한정하면 됩니다.**

1. 워시 발송 키를 실제 서버가 받는 이름·위치와 맞추기.
2. 중복 방지 저장소 오류나 발송 결과 불명 상태에서 무조건 다시 보내지 않도록 처리하기.

이후에는 새로운 기능 요구 없이, 실행 가능한 최종 묶음으로 핵심 흐름을 한 번 확인하고 운영 적용·시험 수신을 마감하면 됩니다. 실제 운영 적용은 여전히 미실행입니다. 이번 검수는 배포 지시나 배포 승인이 아닙니다.

기존 시험기 판정 오류는 수정됐습니다. 제가 첨부 시험기의 자체 검사 28개를 직접 실행해 모두 기대 결과와 일치하는 것을 확인했고, 필수 입력 누락 시 종료 코드 2도 확인했습니다. 이 부분을 다시 수정하도록 요구하지 않습니다.

### 중복 방지 함수 재현 방법과 한계

첨부 워시 sb27→sb28, 체크 v52→v53 diff에서 추가된 `idemRun`과 관련 선언을 추출했습니다. Node 내장 TypeScript 변환으로 실행하고, 메모리 DB 및 메모리 처리 콜백을 주입했습니다. 실제 DB·솔라피·운영 API는 호출하지 않았습니다.

위 8개 시나리오는 실제 첨부 함수의 분기를 실행한 결과입니다. 처리 횟수는 메모리 콜백의 횟수이며 실제 고객에게 메시지가 두 번 갔다는 뜻은 아닙니다. 실제 발송 함수가 응답 유실을 어떻게 처리하는지는 서버 전체 원본과 통합 시험으로 확인해야 합니다.

## 출시 전 수정 1 — 워시 발송 키 연결 (P1)

워시 화면 v142 diff는 발송 payload에 `sendKey:String(o.id||'')`를 추가합니다. 워시 보고서도 이 키를 서버가 처리해야 한다고 명시합니다.

반면 sb28 diff의 새 진입부는 본문 최상위 `body.rid`가 소문자·숫자 24자리이고 기능이 허용 목록에 있을 때만 `idemRun`을 사용합니다. `sendKey`를 처리하는 새 코드가 이 diff에는 없습니다. 총괄 README도 워시의 rid 연결을 ‘다음 판’으로 남겼습니다.

따라서 화면 57개 시험 통과를 서버 중복 발송 방지까지 통과한 것으로 해석할 수 없습니다. 기존 기준 서버에 별도의 동등한 보호가 있다면 그 코드와 통합 결과로 보여주면 되고, 없다면 최상위 rid로 통일하세요.

**최소 완료 기준**
- 같은 업무·같은 발송의 재시도는 같은 유효 rid를 보냄.
- 동시 클릭·서버 접수 뒤 응답 유실 후 재시도에서 실제 공급자 접수는 1회.
- 사용자가 의도적으로 ‘다시 보내기’를 선택하면 새 업무 키.
- 기존 sendKey를 유지한다면 서버의 원자적 소유 획득·결과 재사용까지 구현하고 같은 시험으로 검증. 단순 변수 이름만 추가하면 부족.
- 알림톡→문자 대체 발송은 한 발송 업무 안에서 처리해 성공 재사용과 충돌하지 않게 함.

## 출시 전 수정 2 — 오류 시 중복 방지 해제 금지 (P1)

워시·체크 두 함수 모두 insert가 23505 이외의 오류면 `return await run()`으로 진행합니다. 표 미적용뿐 아니라 권한·DB 장애 등에도 같은 동작이 됩니다. 결과의 done 업데이트 오류도 반환 객체의 error를 확인하지 않습니다. 5분 넘은 run 행은 지우고 재실행합니다.

기록 upsert의 동일 ID 재저장은 가능하지만, 메시지 발송 같은 외부 부작용까지 같은 정책을 쓰면 안 됩니다.

**최소 수정 방향**
- 알림 발송에서 중복 방지 claim을 확보하지 못하면 공급자를 호출하지 않고 재시도 안내.
- done 저장 오류를 감지하고, 이미 접수됐을 수 있으면 ‘확인 중’으로 남기기.
- 타임아웃·응답 유실·프로세스 중단을 ‘보내지 못함 확정’과 구분. 결과 불명 상태를 삭제하거나 5분 후 자동 재발송하지 않기.
- 확인 중인 메시지는 공급자 요청/그룹 ID 조회 등으로 결과를 확인한 뒤 처리. 확인 방법이 당장 없으면 자동 재발송을 막고 운영자가 확인하도록 표시.
- 오래된 작업 재획득은 읽기→삭제→insert로 경쟁하지 말고 조건부 원자적 변경으로 수행. 기존 작업이 아직 살아 있으면 중복 실행되지 않아야 함.
- 전체 메시징 시스템을 새로 만들 필요는 없음. 이번 핵심 발송 경로에 한정해 안전한 재시도와 상태 표시를 마감.

## 개발 외 마감 조건

### A. 실행 가능한 묶음

이번 zip은 diff와 결과 보고가 중심입니다. 전체 서버 sb28/v53/d9, 화면 v142/v56.6/기사 v29, `fake_supabase_*.ts`, `import_map_*.json`, 워시 미리보기 생성기의 기준 파일이 빠져 있습니다. 따라서 제출자가 기록한 전체 시험을 이 묶음 하나로 다시 실행할 수 없습니다.

다음 제출에는 필요한 전체 파일과 시험 의존 파일을 함께 넣으세요. 같은 내용을 새로 설명한 문서 여러 개보다, 로컬 명령 한 번으로 돌릴 수 있는 묶음이 필요합니다. 기존 고객 자료·비밀키는 넣지 않습니다. 새 검토 범위를 추가하는 요구가 아니라 이미 약속한 직접 실행을 가능하게 하는 제출 조건입니다.

### B. 운영 적용 순서

현재 실행 순서 한 장에는 SQL 24와 서버 배포는 있지만, 이번 멱등 보호의 필수인 SQL 26이 빠져 있습니다. 최소 순서를 한 장으로 통일하세요.

1. 운영 버전·DB 제약·RLS·Storage 비공개·레거시 접근 상태를 읽기 전용으로 확인.
2. 기존 중복에 대한 보호 계획과 백업/되돌리기 방법 확인.
3. 승인 후 필요한 SQL 24 및 **26** 적용·정의 확인.
4. 승인 후 sb28/v53 서버와 대응 화면 v142 후속판/v56.6/기사 v29 적용.
5. 지정 시험 업체에서 저장→재로그인, 단일 발송→결과 조회→재시도 차단 확인.

이 보고서를 근거로 지금 SQL이나 배포를 실행하지는 마세요. 기존 중복 정리도 승인 없이 하지 않습니다. 정리 전에도 신규 중복을 막을 수 있는 설계인지 확인 후 적용해야 합니다.

### C. 알림톡 실제 설정

동봉 템플릿표에서 실제 템플릿 ID·채널 설정은 ‘관리 확인 필요’입니다. `check_remind`는 승인 여부 미확인/등록 대기이고, 승인 전에는 문자 대체·매일 자동 불가로 적혀 있습니다.

따라서 ‘청구서·재검사·도착 알림톡 모두 가능’이라고 묶어 확정하면 안 됩니다. 내일 필요한 알림별로 설정과 실제 시험 수신 결과를 확인하세요.
- 입고·출고·청구서·입금 확인: 실제 사용할 항목만 수신자·치환값·사진/기록 링크 확인.
- 체크 재검사 알림: 승인·코드가 확인되기 전에는 **알림톡 미확인**, 자동 알림톡은 열지 않기. 문자로 운영할지는 비용과 함께 별도로 결정.
- 요청 접수와 최종 전달 성공을 구분. 발송 대행사의 접수만으로 ‘휴대전화 수신 완료’로 판정하지 않기.
- 공급자 응답 유실은 요청 미접수 확정이 아님. 이때 곧바로 다른 경로의 문자를 보내면 중복 가능성이 있으므로 앞의 오류 처리와 함께 검증.

단가·승인 상태·실제 수신은 이번 코드 검수에서 외부 계정으로 확인하지 않았습니다.
